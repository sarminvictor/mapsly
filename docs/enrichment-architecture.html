How enrichment actually runs

The get-leads enrichment engine — how Lighthouse and every other research family is executed, the dependency order between them, and the honest answer to “why a cron and not the Boxly Worker queue?”

① The short answer

🎯

There are two separate background systems. The Boxly Worker (a real Redis queue with concurrency + retry) handles the older flows — website scans, search scans, ad scans, bulk review pulls, business qualification. But the new agency get-leads enrichment (contacts, Lighthouse, reviews, services, AI) does not use the Boxly Worker — it has its own cron-drained job rail (EnrichmentRun → EnrichmentJob rows in Postgres, drained by /api/cron/internal/dispatch). That’s the source of the confusion.

Why it was slow (before the fix)

  • Each Lighthouse audit is a synchronous DfS Live call (/on_page/lighthouse/live/json) that blocks ~10–30 s while DfS runs the real audit.
  • Jobs ran one-at-a-time, 25 per tick, and a tick only fired on the every-2-minute cron.
  • 73 × ~10 s sequential ≈ 12+ minutes. 😖

Why reviews were already fine

  • Reviews use DfS Standard queue + pingback webhook: we submit the task and DfS calls us back when it’s done — no blocking.
  • So the “webhook per business” model you were thinking of already exists — for reviews. Lighthouse just never adopted it (it uses the blocking Live call).

② Two background systems

Both exist to keep long work out of the user’s request (the hard rule: no live external API in a user request path). They differ in who runs the queue.

  System A · Boxly Worker System B · Cron job rail
Queue lives in Redis (the sibling Boxly product) Postgres — EnrichmentJob rows (status QUEUED→RUNNING→DONE)
Who drains it The Boxly worker process (its own concurrency + retry), calls back to Mapsly endpoints /api/cron/internal/dispatch → dispatchPending()

③ The enrichment pipeline (System B)

What happens from the moment you click Enrich. The heavy work never runs in your click — the action only writes a PENDING row and returns; the dispatch drains it.

④ The dependency order (DAG)

Not every family is independent. The DOM scrape (the Contacts job) is the root: it captures the page once, and two families read that captured DOM — so they can’t start until Contacts finishes for that business. The dispatch enforces this without a schema: a business’s dependent jobs aren’t claimed until its Contacts job is terminal.

🔗

Tech has no job of its own. Selecting the “tech / DOM” signal just adds cost to the Contacts job — one page fetch produces both the contacts and the tech fingerprint. That’s why the checklist bucket is “Contacts” + a combined “Website & tech” row.

⑥ Lighthouse deep-dive (the slow one)

One Lighthouse job, step by step

  1. Job claimed QUEUED → RUNNING.
  2. Freshness re-check — audited <30 days ago? SKIPPED_FRESH, $0.
  3. No website? skipped (can’t audit).
  4. Open site → cheap DfS Live audit (blocks ~10-30 s).
  5. Cloudflare-walled → fall back to the paid Apify Lighthouse actor (hard-capped per run).
  6. Persist the audit → DONE.

Why 73 took 12+ minutes

The audit itself is the cost — DfS runs a real Chrome Lighthouse pass server-side. Ours were fully sequential, and only 25 ran per 2-minute cron tick. So throughput was ~1 audit / 10s in a single line.

73 × 10s = 730s ≈ 12 min. Exactly what you saw.

✅

Fix shipped: the per-tick job loop now runs 6 audits concurrently (safe — each call is long, so the request rate stays well under DfS’s 10/s), and the dispatch self-chains (re-kicks itself instead of waiting for the next cron). 73 Lighthouse audits should now finish in ~2-3 minutes, and the progress bar climbs honestly the whole time.

⑦ What’s fixed · what’s next

Just shipped

  • Parallel job loop (p-limit 6) — the throughput fix.
  • Self-chaining dispatch — no 2-min gaps between batches.
  • Live progress — unitsCompleted advances every tick, so the header + Enriching page climb 0 → 73 instead of jumping at the end.
  • Honest copy (no fake “we’ll email you”, no “Jobs tray”), stable ETA.
🧭

The real architectural question you raised. There are two cleaner long-term options, both worth a decision:

Option A · Lighthouse → async pingback

Move Lighthouse from the blocking Live call to DfS’s Standard queue + pingback — exactly what Reviews already does. Submit all 73 at once, DfS calls us back per business as each audit finishes. No blocking, no parallel-tuning, per-business progress for free.

Smaller change · reuses the proven review-pingback rail.

Option B · route enrichment via Boxly Worker

Hand the per-business jobs to the Boxly Worker (System A) — the Redis queue that already does concurrency + retry + callbacks for the other flows. The cron rail becomes a thin fallback.

Bigger change · unifies both systems into one queue.

My recommendation: Option A for Lighthouse (fast, low-risk, matches Reviews) now that the parallel+self-chain fix has bought us headroom — and revisit Option B only if we later want a single unified queue across all flows.
