TL;DR The one insight

The user wants DATA. We keep showing them RESEARCHES. Tom doesn't care that "Tech/DOM" is a separate line or that "Contacts" rides the same fetch. He wants emails, reviews, ad activity, site speed for a set of leads. Almost every confusion below comes from leaking our backend research taxonomy (10 "types", 8 jobs, 5 families, 9 badges) into a UI that should speak in data the user gets.
Problem A · Filtering

Two separate places to filter (the + Filter picker and the Coverage layer), and no clear way to say "show me the 34 I actually enriched" vs the 53 that are only discovered.

Problem B · Enriching

Select a few leads, click Enrich — the popup lists every research type as a full-price buy line and never shows what those leads already have. "Enrich 53 · ~139 cr" doesn't say what you get.

Problem C · Flow ↔ UI

The popup and progress step describe researches that aren't real jobs (Contacts + Tech are one fetch; Discovery runs no research; Lighthouse is separate). The UI and backend disagree.

5 The three problems, dissected

A · Filtering a partially-enriched list

Your list is 53 visible / 56 total. Some leads are fully enriched, some partial, some only discovered. You have two filtering tools that don't talk to each other:

  • + Filter → filters by signal verdict or field value ("Emails ≥ 1", "Search visibility = weak"). A lead with no data for that field simply never matches — so it silently drops un-enriched leads.
  • Coverage layer → filters by run state ("Contacts · not run", "Reviews · none"). This is the tool for "partially enriched", but it's hidden in a second panel and speaks in 5 families.

The missing question: "show me the leads I've actually enriched" has no single answer — "Enriched only" counts empty/failed and per-cell runs, so it's not "leads with data".

B · Enriching — what leads, and what do they already have?

You select a few leads, click Enrich. The popup shows every research type as a uniform buy line. It cannot show what those leads already have — the popup is never handed the per-lead run states (EnrichMoreHost passes only {discoveryId, request}). So:

  • "Enrich 53 · ~139 cr" doesn't say what data you'll get, or that 34 of them already have contacts.
  • Picking "Tech" silently adds "Contacts" (a dependency) — surfaced only as a tiny footnote.
  • The net (deduped) price is computed server-side at run time, so the sheet's gross number over-states what you'll actually pay.

C · Research-flow ↔ UI misalignment

The UI describes researches that aren't real jobs:

  • Discovery is shown like a research step but runs no enrichment — it only finds businesses.
  • Contacts & Tech/DOM are two popup rows but one fetch / one job — Tech has no independent cost, fetch, or data pull.
  • Lighthouse shares the "tech" progress bucket in the last step, so selection UI and progress UI group it differently.
  • The progress step's fallback list overclaims — before real data lands it shows "Contacts extracted", "Reviews", "Draft first touches" for every run, even a Lighthouse-only one. "Draft first touches" isn't even part of enrichment.
  • Services / AI advertise "Nd fresh" but have no freshness cursor — they re-bill every run.

7 Gaps & decisions we need to make

Five things are broken or half-built. Each is written as: what a user would notice → why it happens → the call we need to make.

1 · Dead signals  Some signals can never light up — even after you pay to enrich.

8 signals (including "Flying blind", which you picked) are half-built: you can select them, we run the research and charge you, but the code that turns the data into a verdict was never finished — so they stay blank forever.

Decide: hide them, or badge them "coming soon" — but stop letting people pay for a signal that can't answer.

2 · AI research has no door  We built AI research, but nothing turns it on.

It's a real, billable job, yet no signal or button reaches it in the normal flow — only a hidden direct link. So it basically never runs.

✓ DECIDED: make it a first-class "AI brief" data toggle (and fold Services into it — see proposal 6.5).

3 · You get charged twice for the same thing  Services & AI research re-bill on every run.

They show "90d / 30d fresh" in the popup, but they have no memory of the last run — so re-enriching the same lead pays again. The freshness label is a promise we don't keep.

✓ DECIDED: give both a real freshness cursor at 90 days — the same window as Contacts. A repeat run inside 90d is free.

4 · "Runs Google ads" is unreliable  We know who advertises in the market, not which business does.

The Google collector runs fine, but Google (unlike Meta) doesn't tell us the advertiser's website — so tying an ad to this clinic is a fuzzy name match that usually fails. Market-level data is solid; per-business isn't.

✓ DECIDED (updated): build the reliable per-business path — call adsSearch({ target: host }) per business-with-a-website; every returned ad attributes to that business by construction (no fuzzy matching). This replaces the unreliable per-cell fuzzy attribution.
Price = 1 credit / business (~$0.002 raw cost, consistent with contacts/reviews/lighthouse). Google ads moves from per-cell billing → per-lead billing. Cost note: you now pay 1 credit for each lead you actually check (reliable) instead of 1 credit for a whole cell (unreliable) — you only pay for the leads you enrich. Still capture ads_domain + fix the landingUrl mislabel.

5 · "Coverage" shows three different numbers  The same idea is counted /5, /6 and /9 on one screen.

The toolbar badge says have / 6, the coverage panel counts 5 families, the row chip strip counts 9 types. Three totals for "how enriched is this lead" — confusing at a glance.

✓ DECIDED: ONE number everywhere = the enrichment types you buy — 9 today → 7 after the two merges (6.5). Kill the /5 and /6. Tag the 3 market-level types (Meta ads, Google ads, SERP) so it's clear they're shared across the cell. A lead reads "Enriched 4 / 7".

The north star Every enrichment surface should answer three questions in the user's language: (1) what data does this lead have? (2) what will I get if I enrich, and what will it cost after dedup? (3) how do I filter to the leads that have (or lack) a given kind of data? The lead drawer already does #1 well — the table, coverage, filters, and popup should adopt the same honest, data-first model.

8 Ad signals & attribution — the correctness audit

We audited the Meta + Google ad flow end-to-end (you asked "are they working perfectly?"). Short answer: Meta is not — two of its signals are logically wrong, and its one reliable attribution key isn't used on the live path.

8.1 · The reliable key exists for Meta — but we don't use it live

Meta CAN be perfect Meta gives every ad a page_id. Matching Business.fbPageId === ad.pageId is an exact ID join — a primary key, zero guessing. That's how it should attribute.
…but the live agency collector doesn't runMetaAdsForCell searches by a market keyword ("dental kelowna") and never seeds fbPageId, so the ID join is starved. It falls back to fuzzy name matching — and keyword searches usually return only an advertiser facet (no per-ad rows), so most businesses that DO advertise get no ad rows at all.

8.2 · Two Meta signals are logically wrong (P0)

✕ Not advertisingmeasures the opposite

It resolves to "this cell has ≥5 advertisers" — a market number identical for every lead. It has no per-business term, so in a busy market it flags everyone, advertisers included. This is the signal you picked — it was measuring "is dental·Kelowna competitive," not "does this clinic advertise."

✕ Competitors advertisingexact duplicate

Byte-identical to the one above (same key, same ≥5) — they can't give different answers.

✓ FIX: make "Not advertising" read a per-business "this business has 0 active ads" (needs 8.1's real attribution), and make "Competitors advertising" the genuine market signal ("≥N advertisers in the cell"). Two different, honest signals.
