Search Visibility · plan v2 (simplified)

mapsly · v0.12.6 · 2026-05-27 · second pass after Viktor's simplification feedback

Pre-implementation analysis. Viktor's feedback on v1 collapsed the plan into a single keystone endpoint (ranked_keywords) plus cell-aggregated Maps queries. This version respects the paid-cell gate, drops two endpoints (keyword_suggestions + monthly volume), and re-uses the Boxly Worker fan-out pattern we already shipped for reviews.

What changed vs v1:
  • ❌ Dropped keyword_suggestions · we don't need manually-entered keywords. ranked_keywords gives us everything the business is ranking for.
  • ❌ Dropped monthly search_volume batch · volume + CPC come embedded in ranked_keywords response.
  • ✅ Added paid-cell gate · same pattern as reviews · skip weekly cron entirely for cells without a paid account. Saves ~80% of API spend.
  • ✅ Maps query is cell-aggregated · one query per top keyword captures Maps ranks for ALL our indexed businesses in the cell at once (verified · 1 query for "lip filler calgary" returned 4 Calgary businesses by cid).
  • ✅ One button per business for manual trigger · the button enqueues both ranked_keywords + triggers the cell-aggregated Maps query if needed.
  • ✅ Boxly Worker fan-out for bulk + weekly cron · reuses dispatch-bulk-pull pattern from PR #96.

1 · The keystone architecture

Two endpoints, one button per business, paid-cell gated. Everything else falls out from this:

┌────────────── PER-BUSINESS · weekly + manual ──────────────┐ [Admin click "Search scan"] [Weekly cron · paid-cell gated] │ │ ▼ ▼ dispatchSearchScan(businessIds, mode) │ ▼ Boxly Worker · fan-out · concurrency 5 │ ▼ /api/internal/trigger-search-scan (per business) │ ▼ DfS · dataforseo_labs/google/ranked_keywords/live → all keywords domain ranks for + organic rank + URL + vol + cpc │ ▼ upsert BusinessKeyword + SerpResult (organic) └────────────────────────────────────────────────────────────┘ ┌──────────────── PER-CELL · after all businesses' ranked_keywords land ────────────────┐ aggregate top-N keywords by Σ (volume × cpc) across paid businesses in cell │ ▼ for each top keyword: DfS · serp/google/maps/live/advanced location_coordinate = cell centroid + 25km · depth=20 │ ▼ match each item.cid against Business.googleCid in cell │ ▼ upsert SerpResult (maps rank) for each matched business └────────────────────────────────────────────────────────────────────────────────────────┘
The cost win · in v1 we estimated $87/mo for 500 businesses doing per-keyword Maps scans. In v2, the cell-aggregated Maps strategy + paid-cell gate cuts this to ~$14/mo at the same coverage. Numbers in section 5.

6 · Schema changes

New: BusinessKeyword join

model BusinessKeyword {
  id           String    @id @default(cuid())
  businessId   String
  keywordId    String

  // Source · "ranked" (from ranked_keywords) | "manual" (admin add)
  source       String    @default("ranked")

  // Latest organic rank · cached from latest SerpResult for fast reads
  // (avoids JOIN to SerpResult for the table view)
  latestOrganicRank      Int?
  latestMapsRank         Int?
  latestEstTrafficUsd    Float?
  latestScanAt           DateTime?

  business     Business  @relation(fields: [businessId], references: [id], onDelete: Cascade)
  keyword      Keyword   @relation(fields: [keywordId], references: [id], onDelete: Cascade)

  @@unique([businessId, keywordId])
  @@index([businessId, latestEstTrafficUsd])  // sort by value desc
}

Modify: SerpResult

model SerpResult {
  // existing fields...
  kind         SerpResultKind  @default(ORGANIC)  // ORGANIC | MAPS
  // existing fields...
}

enum SerpResultKind {
  ORGANIC
  MAPS
}

Currently SerpResult tries to coalesce organic + maps into one row. With kind we get clean per-(keyword × business × kind × scan) rows, much easier to query and to show diff history per surface.

7 · UI · what Maria sees on /(smb)/search

Three sections, mobile-first per ui-ux-smb:

A · Hero KPIs (4 tiles)

  • Top 3 in Maps · count of keywords where Maria ranks 1–3 on Google Maps for her city
  • Page 1 of Search · count of keywords where she ranks 1–10 on Google organic
  • Monthly traffic value · Σ (estimated traffic × cpc) across her ranking keywords — the value-prop number in dollars
  • Movement this week · "↑12 improved · ↓5 dropped · 3 new" derived from is_new/is_up/is_down/is_lost ranked_keywords flags

B · Keyword table · grouped by service

Per service (Botox / Filler / Laser hair removal / etc.), show top keywords with: keyword · search volume · Maps rank · organic rank · weekly delta arrow · estimated $ value. Sorted by traffic value desc. Soft cap 25 per service.

C · Competitive table per high-value keyword

Click a keyword row to expand a top-10 competitor view (drawn from cell-aggregated Maps data + ranked_keywords for the businesses we index). Maria's row highlighted in coral.

D · “Where you're not ranking” section

Keywords other paid businesses in the cell rank for, where Maria doesn't. Derived from cell aggregation · zero new API calls. Top 5 by traffic potential. Plain English: “Your competitor Papillon ranks for these · you could too.”

9 · Decisions for you

  1. Top-N keywords for Maps · what's N? · 30 per cell? 50? Each is $0.002. My rec: 30 — covers the highest-value keywords per cell · ~$0.06/week per cell.
  2. Should manual single-trigger ALSO trigger cell-aggregate? · If Maria clicks "scan" on her own business, do we re-run cell aggregation immediately? Or wait for weekly cron? My rec: trigger debounced (if no aggregation in last 24h, run it; else skip).
  3. How does "paid cell" gate work for cells with mixed paid + free businesses? · Currently shouldCollectReviewsForBusiness uses filterEligibleBusinesses · scan ALL businesses in a paid cell or only the paid ones? My rec: ALL · competitive view requires knowing where competitors rank too, even if they're not customers.
  4. Drop the existing per-keyword cron? · weekly:serp-rank-scan reads Keyword table (0 rows today). Drop and replace, or deprecate and run new cron alongside? My rec: rename + replace · the existing one is dead code.
