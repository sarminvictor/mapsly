Executive verdict

This is impressively disciplined engineering of the outbound half of a cold-email system — and it is exactly half a system. The send-side hygiene (separate cold domain, plain-text-first, no tracking pixels, link-free first touch, conservative ramp, mailbox rotation, jitter, correct RFC 8058 one-click unsubscribe) reflects real deliverability literacy, above most DIY builds.

But measured against your three stated requirements, it fails all three as shipped: 1,000/week is mathematically unreachable (hard ceiling 750/week at defaults, earliest 1k-week is week 3 after manual changes that have no UI); deliverability is flown blind (zero feedback loops — bounces, replies, and complaints are all invisible); and "fully automated" is contradicted by mandatory daily manual triage of 5 Zoho inboxes. On top of that, every email currently sent violates CAN-SPAM (postal address deliberately removed in v0.15.3, with a unit test locking the violation in), on a provider — Zoho — whose usage policy bans bulk cold email outright.

The good news: the fixes are cheap and the architecture anticipates them. One footer rewire (hours), one IMAP poller cron (days), one alert helper (days), and a second sending domain close most of the gap — or a $47/mo sequencer closes all of it this week.

What's done right verified

  • Separate cold domain. The single most important decision in cold email — mapsly.ai and Resend transactional reputation are fully isolated. Most DIY builds get this wrong.
  • Plain-text-first, zero tracking. No open pixels, no click-wrap redirects, minimal HTML alternative, link-free first touch — exactly the 2026 playbook (HTML-heavy cold email bounces ~6.5× more per Hunter's 2.2M-email study).
  • Correct RFC 8058 one-click unsubscribe, honored instantly (beats the 10-business-day legal floor), with global suppression checked before every send.
  • Conservative, Zoho-tuned ramp with a hard zero-until-activated gate; unit-tested.
  • Self-balancing mailbox rotation — lowest-usage box re-acquired per send; capacity exhaustion cleanly stops the tick.
  • Provider-block circuit breaker — catches Zoho's 421/"5.4.6 unusual sending activity", cools the box 2h, aborts the tick as likely IP-wide.
  • Humanized cadence — small batches, random 2–8s gaps, 0–4h follow-up jitter, business-hours weekday window.
  • Double-send protection by design intent — unique idempotency key + transactional step advance (with one verified hole, see finding #6).
  • Layered kill switches — env hard-override + DB toggle, checked at the top of every tick.
  • Best-in-class cash cost — ~$10–15/mo vs ~$90–110/mo for the equivalent tool stack.

Verified findings

Every finding below was independently re-verified by an adversarial agent instructed to refute it against the actual code. All survived. Ordered by severity for your three goals.

CRITICAL · LEGAL 1 · Every email sent violates CAN-SPAM — postal address deliberately removed

What the code does: buildTextFooter() returns only an unsubscribe link; toHtmlBody() appends only an "Unsubscribe" anchor (modules/cold/template.ts:26–54). The hardcoded PHYSICAL_ADDRESS ("Mapsly · 530 3 St SE, Calgary…", config.ts:67) has zero consumers — dead code that contradicts its own comment ("MUST be a real postal address"). Commit 8d69832 ("drop postal address from footer") removed it, and a unit test now asserts the address is absent — documented willfulness in git history. The setup doc still claims compliance ("legal cold with a real postal address").

Why it matters: CAN-SPAM (15 U.S.C. §7704(a)(5)) requires a valid physical postal address in every commercial email, B2B included. Statutory maximum is $53,088 per email. At 1k/week that's 52,000 violations/year stamped into your own database. CASL (you're a Calgary company) additionally requires a mailing address valid 60+ days in every CEM.

Fix (~15 lines, hours): wire getColdSenderConfig().physicalAddress into both footers, update the 3 call sites, and invert the regression test. A single muted gray line keeps the personal look while satisfying the statute.

HIGH 2 · Replies never stop a sequence — your hottest leads get robotic follow-ups

What the code does: the cron's TERMINAL gate honors REPLIED/WARM statuses (route.ts:34–41,142) — but no code path ever sets them. They are dead enum values. There is no IMAP polling, no inbound webhook, and not even an admin "mark replied" button. A prospect who replies "yes, send me the report" receives touch 2 and touch 3 anyway.

Why it matters: beyond burning your warmest leads, follow-ups to repliers provoke spam-button clicks — and complaint rate is the #1 domain-killing signal (Gmail hard ceiling 0.3%, target <0.1%). At a 3.4% average reply rate, ~34 people per 1,000 reply — every one of them then gets ignored and re-mailed.

Fix: stopgap (15 min): admin markReplied action — the consuming side already works. Real fix (days): one imapflow cron polling imap.zoho.com:993 with the existing creds — which also solves findings 3 and 9 in the same file.

HIGH 3 · Bounce rate is effectively blind — async bounces never suppress

What the code does: bounce capture is SMTP-submission-time only. Zoho is a relay: it answers 250-OK, then the remote server's rejection ("550 user unknown") arrives minutes later as an NDR email into the Zoho inbox — which nothing reads. The async-bounced address stays "delivered" in your data and receives touches 2–3. UNDELIVERABLE suppression-source exists in the schema but is never written.

Why it matters: sustained bounce rate >2% suppresses inbox placement for the whole domain; >5% is long-term destructive. You cannot manage what you cannot measure — and right now the real bounce rate is invisible. Enrollment also doesn't require verified emails (enroll.ts only checks email != null despite its own comment claiming "VERIFIED owner email").

Fix: (a) same-day: gate enrollment on emailVerifiedAt + feed the existing monthly email-verification cron's "undeliverable" verdicts into suppress(); (b) days: NDR ingestion in the same IMAP poller (parse RFC 3464 DSNs → BOUNCE_HARD).

HIGH 4 · Alerting is pull-only — blocks, bounce spikes, and stalls are silent

What the code does: a provider block writes blockedUntil and breaks the tick; the cron closes "PARTIAL" but still returns HTTP 200, so even Vercel's cron-failure indicators never fire. No Sentry, no Notification rows, no email alert — grep-verified. The runbook's mitigation is literally "watch the overview… hit Pause all sending".

Why it matters: a fully-blocked fleet, a bounce spike, or a multi-day stall is discovered only when you happen to open /admin/email. That is the antithesis of "fully automated" — the system can't protect itself or call for help.

Fix (days): sendOpsAlert() via the existing Resend transactional path (never via the Zoho boxes that may themselves be the failure) + Notification rows for the dev dashboard. Wire three triggers: mailbox blocked → WARN; zero capacity while sends due → CRITICAL; trailing-24h hard-bounce rate >3% → auto-set global pause (the kill switch already exists — automate pulling it).

HIGH · GOAL 5 · 1,000/week is mathematically unreachable — hard ceiling 750/week

The math: 5 mailboxes × dailyCap 30 × 5 weekdays = 750/week, permanently. Week 1 of the ramp delivers ≈140 emails; week 2 ≈690; the first possible 1,000-email week is week 3 — and only after raising caps via a server action that has no UI, or adding mailboxes nobody has provisioned. Nothing in the product flags the 25% shortfall. (The runbook itself only promises "~1k cumulative by week 2" — cumulative, never weekly.) Cron headroom is also thin: 8/tick × 32 in-window ticks = 256/day ceiling vs the 200/day the goal needs.

Fix — capacity the safe way: do not raise caps to 40/day on one fresh .xyz domain (concentrates 200/day on a single reputation; best practice is 2–3 boxes per domain, 20–50/day per box). Add 2–3 mailboxes on a second lookalike domain (config already supports COLD_MAILBOX_6..50): 7–8 boxes × 25–30/day × 5 days = 875–1,200/week with per-box volume unchanged and blast radius halved.

HIGH · STRATEGIC 6 · The whole operation rides on a provider whose policy bans it (Zoho)

Zoho's usage policy prohibits unsolicited bulk email outright, and SMTP is throttled to a dynamic, reputation-based 50–500 emails/hour per mailbox. Ban probability scales with exactly the volume you're targeting; a suspension zeroes throughput with no programmatic recourse — and the code's own ramp comment acknowledges Zoho's "unusual sending activity" detector trips early. Industry consensus for cold infrastructure is Google Workspace mailboxes (better deliverability into Gmail, where most of your SMB owners live) or a dedicated sequencer. This is a strategic risk, not a bug — but it caps how far this system can ever be pushed.

MEDIUM 7 · Dispatch is not crash- or concurrency-safe — the same email can send twice

Due rows are fetched as PENDING with no atomic claim (no SENDING state, no SELECT … FOR UPDATE SKIP LOCKED); SMTP fires before the DB write. A crash or transient Neon failure between SMTP-accept and commit leaves the row PENDING → re-sent next tick. Worse: attempts increments inside the post-send transaction, so sustained DB trouble means MAX_ATTEMPTS never engages → unbounded duplicates. The idempotency key doesn't help — re-processing reuses the same row. Fix (hours): add SENDING status + conditional updateMany claim before SMTP + a tick-start sweeper for stale SENDING rows.

MEDIUM 8 · Zero copy variation — byte-identical bodies fingerprint the template

The template engine supports tokens/conditionals but no spintax; every recipient gets an ~85% byte-identical body and 3 fixed subject skeletons from one fresh domain. Duplicate-content fingerprinting is a classic bulk signal; 2026 practice is 3–5 spintax blocks per email. The subject "quick question" is among the most saturated cold-email patterns in existence. Fix (hours): ~15-line {{a|b|c}} spintax pass seeded from recipientId+stepOrder (deterministic across retries), plus 2–3 phrasings per sentence in the 3 default touches.

MEDIUM 9 · No complaint loop, and a mailto: unsubscribe that nothing processes

The COMPLAINT suppression source is dead code; the domain isn't registered in Google Postmaster Tools, so the only complaint metric Gmail provides at this volume is unwatched. Meanwhile the List-Unsubscribe header advertises a mailto: channel that lands in a Zoho inbox nobody reads — advertising an opt-out you don't process is strictly worse than not advertising it (the HTTPS one-click alone satisfies RFC 8058 and Gmail/Yahoo). Fix: register Postmaster Tools today (~30 min); drop the mailto term (one line) until the IMAP poller processes it.

LOW 10 · Manual enrollment; dailyEnrollCap is dead config — plus 45 minor findings

Enrollment is an admin button click; dailyEnrollCap is stored, validated, editable — and enforces nothing. For "fully automated", add a daily auto-enroll cron that tops campaigns up to their cap. Notable among the further 45 lower-priority findings: links point at mapsly.ai from a mapsly.xyz sender (re-coupling the reputations the domain split was meant to isolate); GET unsubscribe fires on link-prefetch scanners (false unsubscribes — POST-only confirm for GET is safer); enrollment doesn't exclude existing customers/claimed businesses; send window is campaign-global, not recipient-timezone; no automated DNS/auth preflight; warm-up is entirely manual and unenforced; setup doc's ramp numbers contradict the code (10→30 vs 3→18); UTC cap reset vs ET send window; per-mailbox health (failedCount) recorded but never displayed.

How I would build it — expert recommendation

The honest call: for your exact three requirements — fastest start, robust deliverability, near-zero manual — buy the sending engine, keep Mapsly as the brain. The $50–90/mo you save by self-hosting has already been spent several times over in build and launch-day fixes, and the riskiest engineering (inbound loops, warm-up, health scoring) is still ahead. Your actual moat — signal-driven lists, personalization data, and the /l/[token] landing pages — stays in-house either way. SMTP plumbing is a commodity someone else operates better for $47/month.

Path A · Recommended — hybrid "buy engine, keep brain"

Time to first send: ~1 day setup · full 1k/week: ~3–4 weeks (warm-up gated — irreducible on any path) · ~$100–110/mo all-in · manual ops ≈ 15 min/week

  • Day 0: register 2–3 lookalike domains (prefer .com: e.g. trymapsly.com, getmapsly.com) + redirect to mapsly.ai. Set SPF/DKIM/DMARC.
  • Day 0: 6 Google Workspace mailboxes (2/domain, ~$50/mo) — Gmail-to-Gmail deliverability where your SMB owners live.
  • Day 0–1: Instantly Growth ($47/mo, 5k emails/mo — exactly fits 1k/wk) or Smartlead Basic ($39/mo). Connect boxes, enable managed warm-up network (the one thing you structurally cannot self-build — Google killed API warm-up; a solo sender has no peer pool).
  • Day 1: wire Mapsly → tool via API: enroll cohorts from your signal engine with personalization variables + /l/[token] report links; consume reply/bounce/unsubscribe webhooks back into ColdSuppression (your suppression stays the source of truth).
  • Weeks 1–3: warm-up runs unattended; start campaigns at low volume in week 2, full volume week 3–4.
  • You get for free: reply detection + auto-stop, NDR/bounce parsing, complaint handling, ESP matching, unified inbox, per-mailbox health scores with auto-pause, deliverability monitoring.

Note: the CAN-SPAM postal address must be in the templates on this path too — fix it in the copy regardless.

Path B · If staying self-built — the 2-week hardening plan

Keeps $0/send economics and full control; accepts Zoho/ops risk. Do not ramp volume until items 1–4 ship.

  • Day 0 (hours): ① restore postal address to both footers + invert the test · ② drop dead mailto: from List-Unsubscribe · ③ register Google Postmaster Tools · ④ gate enrollment on emailVerifiedAt + suppress "undeliverable" verdicts from the existing verification cron.
  • Days 1–3: the single highest-leverage build — one IMAP poller cron (imapflow, imap.zoho.com:993, existing creds): RFC 3464 DSN parsing → auto-suppress bounces; human replies → REPLIED (the gate already honors it); OOO classified separately; mailto opt-outs honored.
  • Days 3–5: push alerting via Resend (never via the cold boxes) + Notification rows; auto-pause circuit breaker on 24h bounce-rate >3% or fleet-wide blocks.
  • Week 2: ⑤ second cold domain + 2–3 mailboxes → 1,050+/week capacity with smaller blast radius · ⑥ SENDING claim state (kill the double-send window) · ⑦ seeded spintax + de-clichéd copy · ⑧ daily auto-enroll cron making dailyEnrollCap real.
  • Strongly consider: migrating boxes Zoho → Google Workspace while the fleet is still small; Zoho's AUP ban is a standing existential risk to the whole channel.
