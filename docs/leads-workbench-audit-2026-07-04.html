Trigger: Barber Shop · Kelowna, CA research · Evidence: live DB verification (scripts/ops/verify-kelowna.ts) + code read of the discover module · Scope: analysis only, no code changed this turn.

§0TL;DR — one bug is behind most of what you saw

Nearly every symptom on your list — the wrong "Enriched" dots, the Coverage panel calling Reviews "Have," the drawer showing "Not enriched" for Ads/SERP that actually ran, the "no email found" cells that still say — enrich — is the same defect wearing different hats:

Root cause · "enriched" is read from data presence, never from enrichment-ran.
The workbench decides a data family is "enriched" by asking "is there a row / a number for it?" instead of "did we run that enrichment on this lead?". Because discovery already fills Business.reviewCount, rating, and identity, every un-enriched barber falsely reads as 2–4 families enriched. And because Ads/SERP ran but found nothing (no rows written), they falsely read as "not enriched." Presence ≠ ran. Fix that one thing and the dots, the coverage panel, the drawer, and the status copy all become honest at once.

The booking "0 results" is a second, self-contained bug (a mis-wired signal binding — §2). Everything else is enrichment-flow UX and missing columns. There is no data-loss problem — the DB already holds the booking-tool names, the socials, the SERP ranks, and the ad-run outcomes. The workbench just isn't showing them, or is labelling them wrong.

§2bBooking signal — why "No online booking tool" returned 0

This is a real, isolated bug, and the DB proves the data is fine: 8 Kelowna barbers have a detected booking tool — Square Appointments ×5, Fresha, Setmore, Vagaro — all sitting in BusinessTech.name. So "0 results" is wrong three times over:

  1. Mis-wired binding. The card "No online booking tool" binds registry key gbp_no_booking, which reads Business.gbpHasBooking — the Google-profile "Book" button (false for all 86 barbers). But the card's UI offers on-site tool chips (Calendly / Vagaro / Square…), which are the tech-fingerprint signal has_booking_widget. The code even documents the mismatch in a comment (goal-templates.ts:1216).
  2. Tool → boolean type clash. Because it's a platform tune (tool chips), the evaluator calls matchPlatform(toolNames, resolvedValue) — but the resolved value is a boolean (gbpHasBooking). Matching "square"/"vagaro" against false matches nothing → every row scores false → 0 results.
  3. Tool name never exposed. Even if re-bound to has_booking_widget, the resolver (signal-eval.ts:686) returns a bare t.hasBooking boolean — not the tool name. Only cms_platform returns a name string. So the specific service (Square/Vagaro/Fresha) — which you asked to see and save — is collected but has no path to the UI.

A fourth, softer issue: booking needs a tech scan, and only your 34 tech-enriched leads have one → the verdict is null (not-computable) for the rest. That's honest (better than a fake "no booking"), but combined with the 0-match bug it made the filter look completely dead. → Fixed by TODO C1–C3.

"Phone-only shouldn't count as booking": agreed — a phone number is a contact channel, not a booking method. The current copy ("Phone-only — friction vs competitors with instant booking") is actually on your side, but the signal must key off tool absence, not phone presence. C1 makes that explicit.

§3The one root cause, in detail — and the fix that ends it

Three surfaces each re-derive "enriched" their own way, all from presence:

Surface How it decides "enriched" Result on a discovery-only barber
Table "Enriched" dots
family-coverage.ts 		identity: true always · reviews from reviewCount != null · website from any tech/LH row FALSE + shows 2–4 dots though nothing ran
Coverage panel
"Have / Not yet" 		Same derivation — Reviews "Have" because a GBP reviewCount exists FALSE + "Reviews: Have" though 0 reviews pulled
Drawer accordions
lead-detail.ts 		reviewsEnriched = reviewCount != null · adsEnriched = ads.length > 0 · serpEnriched = serp != null BOTH Reviews false-+; Ads/SERP false-− (ran, found nothing → "not enriched")
The fix — one canonical state, derived from run records.

Define a per-(lead × enrichment) state enum, sourced from what actually ran, not what rows exist:

State Source of truth Meaning
not run no EnrichmentJob / AdMarketRun for this (lead, type) never attempted — costs credits to try
running / queued job RUNNING / QUEUED in flight
enriched job DONE and data written ran, found data — show it
no data job DONE but zero rows ran, nothing exists (Ads/SERP for barbers) — calm grey, don't re-charge
failed job FAILED (retries exhausted) errored — red, retry affordance

The plumbing already exists: EnrichmentJob tracks job-backed families (contacts/tech/reviews/lighthouse/ai) with DONE/FAILED/SKIPPED_FRESH, and AdMarketRun tracks the cell-scoped ones (ads/serp) with status + counts. deriveFailedFamilies() already half-does this. The work is to make one state function every surface reads — replacing the three presence heuristics.

This is exactly the model Clay and Apollo converged on (per-cell state; "Unavailable" ≠ error). See §6.

§6Competitor benchmark — Clay, Apollo, Ocean

Where do best-in-class enrichment tables solve exactly these problems? Two products set the bar, and both converged on the per-cell state model we're proposing in §3.

Clay — column = enrichment, cell = a job

  • Each enrichment is a column you add; every cell carries independent state: empty · "waiting for inputs" (blocked) · running · found · not found · error (red, click to diagnose).
  • Retry unit is the cell ("re-run this cell") — not the row, not the column.
  • Cell-details side panel = provenance (raw response, source, confidence).
  • Waterfall providers stop on first hit → you pay until a hit, not per provider.

Adopt: the 5-state enum (§3), cell-level retry, the provenance panel (you already have a drawer), waterfall for contacts (you already run one).

Apollo — reveal + verified badge

  • Locked field shows an in-cell "Access email · 1 cr" button — price is in the cell. Reveal = spend + save, coupled.
  • Revealed value carries a trust badge: Verified · Likely · Guessed · Unavailable (the calm "no data exists" terminal — grey, no re-charge).
  • Email-status filter → filter the list by state (your C5).
  • Saved views (layout + filters, named) — you already have this primitive via goal-in-URL.

Adopt: in-cell Run · N cr (D2/A4), the "Unavailable" ≠ "failed" split (A4/A5), state filters (C5).

Ocean.io — pre-spend preview · and your unique edge

Ocean shows a result/eligibility preview before you spend. Adopt for bulk runs: "Enrich 240 leads · 190 eligible · ~380 cr · balance 3,200" — turning the wallet from a constraint into a trust feature (your best defense against "why was I charged for nothing").

Your genuine differentiator (no competitor solves it): the market-cell vs lead-level split. SERP/ads are per-geo-cell, shared across many leads; contacts are per-lead. Render market-level enrichments as a shared, once-per-cell column ("SERP · scanned 3d ago · shared across 40 leads · 1 cr") so Tom never thinks he's paying N times. This is downstream of your signal-vocabulary moat — an opportunity to invent, not a gap to close.

Footnote: the "Origami" you mentioned is origami.chat — a prompt→finished-list generator (natural-language Clay), not a per-cell enrichment table. No adoptable table patterns; it's a competitor to your discovery flow, not this workbench.

The height problem — quantified

The grid is capped, not filled. This is the single highest-leverage fix.

The workbench is a plain body-scrolling <div> with no height/flex context, so the data grid can only be sized by a fixed max-height:62vh on .wbtable-wrap (agency-portal.css:1929). It can never flex to fill the space below the toolbar, and everything above is fixed chrome that eats the viewport first. Opening the inline Filters/Coverage panels (fully uncapped) pushes the capped table further down.

The math @ 900px: 62vh = 558px. Above it: topbar 60 + top-pad 30 + WorkspaceHeader ~145 (32px serif h1 + goal pill + wrapping note) + tabs ~64 + toolbar ~46 + chips ~46 = ~391px (~43%) of fixed chrome. With a 35px sticky header and ~35px rows, the box shows only ~14–15 rows and runs past the fold → double-scroll. On a 24″ monitor the cap wastes ~38% of vertical space (~8–12 rows that could show but don't).

The fix (U1+U7): make the workbench root a flex column height:calc(100vh - var(--sticky-offset)); overflow:hidden; header/tabs/toolbar/chips become flex:0 0 auto; .wbtable-wrap becomes flex:1 1 auto; min-height:0; overflow:auto; delete max-height:62vh; keep the sticky thead. Convert Filters/Coverage to popovers on #agency-overlays so opening them costs zero grid height. Add a Compact density default (~28px rows). Net: ~14 → 25+ visible rows and the double-scroll dies in one change.

§9Actor reliability — the Meta Ad Library scraper

"Ran · OK · 0 advertisers" is only trustworthy if the run reached Meta and genuinely found nothing. The live Apify logs say that's true less than half the time — and the app can't tell the difference. Evidence: the live Apify API (96 runs) + per-run logs + the actor source + the app-side adapter.

The core defect: SUCCEEDED means "the process didn't crash" — not "I got trustworthy data."
A blocked run, a proxy-timeout run, and a genuinely-empty market all exit 0 with 0 items. The adapter reads an empty dataset, records AdMarketRun = OK/0, and caches it for 6 hours — and we paid Apify either way. There is no signal that separates "blocked" from "empty," even though the actor logs one (graphqlHits) and then throws it away.

How it works now

Apify + Crawlee PlaywrightCrawler, one warmed browser session (maxConcurrency:1) on Apify RESIDENTIAL proxy, country-matched. It primes on facebook.com (waitUntil:"load") to acquire a datr cookie, then navigates each Ad Library search URL and intercepts /api/graphql responses to extract (a) the advertiser facet (dynamic_filter_options.pages) and (b) per-creative ad nodes. A graphqlHits counter is the block/empty discriminator — 0 = the data query never fired (blocked), ≥1 = a real result (even if 0 ads). A blocked target retries 4× re-warming the same session; images/fonts are aborted to save bandwidth.

The adapter (services/apify/meta-ad-library.ts) partitions the dataset items into rows / resolutions / advertisers — and receives no run status, no graphqlHits, no blocked flag. Empty items → {rows:[], advertisers:[]}, wrapped in a 6h KV cache (line 175), billed to the CronRun regardless of yield.

Honest nuance: some of those 30 zero-item runs are genuinely empty markets (Kelowna barbers don't advertise — legitimately 0). The failure isn't "half the runs break" — it's that the system cannot tell a block from a timeout from a real empty. The logs prove the discriminator exists: botox Miami: 0 ads, graphqlHits=0 (blocked) vs dermal fillers: 0 ads, graphqlHits=1 (genuinely empty) — but it never leaves the log.

Root causes

  1. The discriminator is thrown away. graphqlHits is logged, never emitted to the dataset → the app can't classify the outcome.
  2. Single residential IP, no rotation. sessionPoolOptions.blockedStatusCodes:[] disables session retirement; one bad IP zeroes the whole run. And Apify residential IPs die in ~60s, so re-warming the same session re-hits a dead IP — the 4× retry loop is often retrying a corpse.
  3. Primer is a single point of failure. One request, waitUntil:"load" (heavy); if it ERR_TIMED_OUTs, the scrape handler never runs — 0 items, exit 0.
  4. Silent success. Primer-fail / all-blocked still Actor.exit() 0; no Actor.fail(), no run-summary record.
  5. Sequential targets blow the 300s cap when re-warms stack up mid-run.
  6. 6h cache poisoning. A blocked [] is cached for 6 hours; re-triggers keep serving empty.
  7. We pay for the ~50% no-yield runs (residential proxy + compute), with no per-outcome cost visibility.

Benchmark — official API & how the mature actors do it

There is no official API for US/CA commercial local-business ads. The scraper is load-bearing.
Meta's developer ads_archive API is scoped to political + social-issue ads; commercial ads are in the archive only if delivered to the UK/EU (DSA-driven), and there's no advertiser-count-by-keyword facet. The full Content Library API is researcher-gated (~$371/mo + $1,000 setup, CASD). So for your actual market (US/CA SMBs) the API can't replace or even fully cross-check the scraper — only calibrate it on EU/UK cells.
What mature actors do What we do
Fire the GraphQL query directly — use the browser only to harvest datr/lsd/doc_id, then page.request.post('/api/graphql') + cursor-paginate. The graphqlHits=0 class can't happen if you fire the query yourself. We wait for the UI to happen to fire the query and count hits — so "0 because it never fired" is our #1 silent mode.
Rotate the IP on block (SessionPool of 5–10; session.retire() on block). Pay-per-result pricing forces them to rotate, not re-warm. Single session, re-warm the same (often-dead) IP.
Residential + rotation, not exotic stealth. None document camoufox/undetected browsers — the reliability is rotation + GraphQL interception. Our 403→recover proves fingerprinting isn't the bottleneck. Don't chase stealth — fix rotation.
curious_coder ~$0.75/1k ads · apify/facebook-ads-scraper claims "99.9% runs succeeded." ~47% productive at a few cents/run — cheap per run, expensive per useful run.

Reliability-engineering best practice (Google SRE · AWS · Crawlee docs): "success = reached the data query and the result is trustworthy," a machine-readable outcome taxonomy (ok · empty_verified · blocked · timeout · partial · error), Actor.fail() with exit codes so status means something, exponential backoff + full jitter with a token-bucket retry budget, a circuit breaker on block-rate (stop burning proxy $ when Meta hard-blocks), negative-cache only verified-empty (short TTL), and success-rate SLOs (block-rate / zero-yield-rate) — not success-count.

The engine reaches Meta and parses correctly; it just can't tell you whether it did.

R0 Make "success" mean something + rotate the IP

Why: ends silent failure — the root of the whole problem. How: emit a RUN_SUMMARY record (per-target ok / empty_verified / blocked / timeout from graphqlHits + a canary assertion); Actor.fail() (exit 1) on block/primer-fail/timeout, exit 0 only on ok/empty_verified; rotate the IP on block (SessionPool 5–10, session.retire() — don't re-warm a dead IP); the adapter reads run status + summary, not items.length; cache only empty_verified (short TTL), never a blocked "0".

R1 Un-zeroable primer + fire GraphQL directly

Why: kills the two biggest silent modes by construction. How: primer retries on a fresh IP, waitUntil:"domcontentloaded", 20s timeout, alternate endpoint (/ads/library/), pre-seeded datr pool; and harvest datr/lsd/doc_id then page.request.post('/api/graphql') + cursor-paginate so the data query can't "fail to fire."

R2 Stop paying to hit a wall + never lose a target

Why: cost + completeness. How: circuit breaker on block-rate (cooldown + half-open probe); token-bucket retry budget + full-jitter backoff; per-outcome costUsd to CronRun.meta; dead-letter + re-queue of blocked targets on fresh IPs; split multi-target runs to stay under the 300s cap.

R3 Observability + honest ceiling

Why: make reliability measurable + defensible. How: SLO tiles on dev.mapsly.ai (block-rate / zero-yield-rate / verified-empty-rate), error-budget alert that gates actor changes, a separate alert for an error-spike (= Meta changed the payload — our prior incident); EU/UK ads_archive cross-check to calibrate the block detector; a paid API (ScrapeCreators/SerpApi) as a last-resort fallback for stubborn blocked cells. The honest ceiling: ~85–92% productive browser-only, ~98% with re-queue + paid fallback. 100% is impossible against a hostile target that can rotate doc_ids at will — which is exactly why the taxonomy matters more than the last percent: it makes failures visible, attributable, and retryable instead of silent.

Same discipline for the DOM-fetcher actor (apify-actors/dom-fetcher/, the contacts/Lighthouse fetcher — the original ERR_TIMED_OUT at blkmktsmp.com was a dead URL burning its retry ladder): canary + RUN_SUMMARY + fail-loud + fresh-IP retry apply verbatim.
