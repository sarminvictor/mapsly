Part C

The Meta actor story — why it failed 3× and where your 43/15 advertisers went (S2)

  • Structural timeout: one actor run gets up to 60 page-targets (meta-ads.ts:64-68) with a hard Apify timeout of 280s (services/apify/client.ts:166). At ~4–10s per target that cannot finish. Your per-market failures — and the identical rerun failure — were deterministic, not bad luck.
  • The salvage that half-exists: the client CAN read a timed-out run's dataset and classify a data-bearing timeout as "partial" — but three bail paths throw the data away: (1) the local poll deadline (295s) throws before reading the dataset when Apify queue/boot time eats the 15s margin (client.ts:226-232) — this is exactly the "actor delivered 43/15 but the app shows nothing" mechanism; (2) the Boxly worker caps the callback at 120s vs the ~300s the route needs (enrich-worker-dispatch.ts:124) — it abandons and retries, starting duplicate actor runs; (3) meta-ads.ts:358-379 hard-discards rows/advertisers whenever outcome=timeout, even when non-empty.
  • Unrecoverable by design: AdMarketRun stores no Apify run id and no error detail — a run that finishes after we bailed can never be found again; diagnosing failures requires console logs.
  • Money: failed cells correctly bill you 0 credits (the earlier fix works). But we pay the actor for every timed-out run, and the deadline-throw path doesn't even record that spend.
Your decision, honored in the design: timeout-with-results = SUCCESS. The fix set below (G · Meta rows) makes every bail path salvage the dataset first, persists partial advertisers as PARTIAL (which auto-bills via the existing OK/PARTIAL gate), stores the Apify run id for late completion, and chunks targets to ≤15–20 per run (~4 runs × ~100s ≈ $0.18/cell) so timeouts stop being structural. Raising the timeout alone (280→420s) is included as a cheap option but chunking is the real fix.
