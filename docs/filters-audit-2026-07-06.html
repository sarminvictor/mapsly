1 · Verdict & scorecard

The three-menu model (+ Signal / + Field / + Data state) is the right architecture and the strict-honesty instinct behind it is correct. But today the system fails Tom in three compounding ways: correctness (five signal families return verdicts on data that was never collected, and the #1 review-management filter is bound to the wrong metric), coverage (only 6 of ~20 filter-worthy numbers are filterable; lead status isn't filterable at all), and transparency (five server-side filters shape the set before any chip runs, and every value a filter reads can be weeks-to-months old while the tooltip fabricates "fresh").

2 · How filtering actually works today (mechanics)

Four independent AND layers run client-side over the loaded window (≤1,000 rows, ordered reviewCount-desc): search (name / address / built-on) → filters[] (numeric + signal chips, every chip must pass) → Enriched only (a fourth filter living outside all three menus) → data-state filters (OR within a group, AND across groups). Then sort; nulls sink. Three different null semantics: a signal chip never matches a null verdict (honest opt-in), a numeric chip silently drops null-valued leads (invisible exclusion), a state filter treats missing matrix rows as all-not_run.

  • Gating asymmetry: + Signal requires a non-null verdict on every loaded row; + Field requires only one row with data; + Data state requires the state's count > 0. Same popover, three honesty standards.
  • Seeding: on first visit, fully-computable goal signals auto-apply as "matched" chips (your two chips "Operating business · Has a website" — auto-seeded, not user-chosen). Saved localStorage beats the URL for numeric filters, while fs= state filters always apply — the documented "URL wins wholesale" contract is broken both ways.
  • Persistence map: numeric filters → localStorage + URL (f=) · signal filters → localStorage only (a shared link silently drops them) · state filters → URL only (fs=) · vsCell/group/columns/density → localStorage · active columns → cookie (for server heavy-field serialization).
  • Heavy fields: the 6 filterable fields are deliberately always-serialized CORE fields; the 8 heavy lazy fields (seo, ad counts, serpRank, aiSummary, bookingTool, socials, pitchAngle) have no filter entries at all — you can never filter on unfetched data, but you also can never filter on it once fetched.

Contacts, reviews and ads signals return verdicts on data that was never collected. P0 CONFIRMED ×3

Three resolver families skip the scanned-guard the rest of the system relies on: contacts counts (signal-eval.ts:723-740 — “Thin / no social presence” reads matched on unscanned leads), review counts (608-614 — unanswered-negatives reads ✗ on never-pulled leads), ad counts (661-679 — “not matched” includes never-scanned leads as verified ad-free). A data-state filter can become invisible and unremovable — hiding every lead you just paid to enrich. P0 CONFIRMED

5 · Stale data in filters — the honest mechanics

The second half of your question: every value a filter reads is cached on one of three clocks, none of which the filter UI mentions. (1) Discovery-time listing fields — rating, review count, website, closed — serve for up to 182 days and both gate rows and feed the Reviews/Rating filters. (2) Enriched values serve inside their billing freshness windows (30d tech/ads/serp/lighthouse · 90d contacts/reviews/AI) during which re-enrich is a deliberate $0 skip — so “verified none” can be a 90-day-old verdict. (3) The evaluation layer reads latest-row-wins with no age guard — latest snapshot, latest audit, best-ever SERP rank. Verdicts are recomputed live, but over frozen inputs.

Why isn't it shown? Because freshness accounting was built for billing, not for filtering. The timestamps exist and are already threaded to the UI (cell tooltips, drawer “as of”, header freshness chip) — but the pipeline strips them before filters run: WorkbenchLeadRow carries plain numbers with no per-field dates, so by the time a chip evaluates a value, its age is unrecoverable. The one freshness word in the filter path is fabricated from run-state (“enriched” → “fresh”). And the compound effect: the enrich scope was itself filtered (pre-enrich filters + best-N), so applying any visible chip today silently re-applies last month's invisible enrich scope — “Lighthouse < 50” really means “was in the enriched subset AND its possibly-months-old audit scored < 50”, evaluated over the first 1,000 rows of a market ordering that can itself be 6 months old.
