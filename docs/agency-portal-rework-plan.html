Mapsly Agency Portal — Demand-Driven Discovery, Enrichment & Expert Signals

A complete implementation plan: switch from supply/cron crawling to on-demand discovery of the live Google-Maps market by metro × category (Cells), enrich it selectively with cost-gated background jobs, surface a per-vertical expert signal layer (med-spa HIPAA, ADA risk, …), and generate personalized first-touch — beating Apollo / ZoomInfo / BrightLocal / Origami on the signals they can’t see.

Executive summary

Mapsly is supply-driven today (admin seeds cells → crons crawl → portal filters whatever is indexed). The rework flips it to demand-driven: the user states intent → picks metros + categories → Mapsly discovers the live market on demand → shows a complete raw list → the user spends money selectively to enrich it → reads comparative, explained signals → generates personalized first-touch.

Key finding from the live-code audit: the substrate is more built than assumed — and that de-risks the rework. TrackedLocation already is the Cell (@@unique([categoryId, city, province, country]) + lat/lng/radiusKm). Discovery is already on-demand (DiscoveryRun). Raw DfS capture is already rich (sourceRawJson, hours, attributes, isClaimed). Scoring v2 already grades 5 market-relative pillars by cell percentile. The agency routes (hunter/lists/list-detail/prospect) are fully built, not stubs. The rework is mostly additive layering — the only risky migration is one unique-constraint swap (city → metro).

The moat (why we beat the four competitors)

Not the data volume — Apollo/ZoomInfo have more contacts. It’s (1) local-business signals competitors are structurally blind to (reviews, ads, SERP, Lighthouse, DOM/tech), (2) a per-vertical expert layer (regulations & nuances — HIPAA cues from reviews), and (3) signal-grounded outreach (~25% reply vs ~2% cold). Positioning: “Origami finds them; Mapsly tells you why to call and what to say.”

3 · Target architecture

The demand loop, and how we keep the hard rule “no live external API in the user request path” intact.

Reconciling the hard rule (no live API in request path)

The rule stays verbatim. Every external call (DfS, Apify, AI, SMTP) runs in air-gapped background workers; the request only mints a job row + publishes a message and returns a jobId; the UI polls (TanStack 3–5s) or SSE-streams progress + partial results.

Orchestration: Vercel Queues for single-shot jobs, Vercel Workflow DevKit for durable multi-step / callback flows (retries, sleep+hook.resume for DfS pingbacks) — retiring the Boxly worker for reviews. Redis token buckets (the existing lib/cache ioredis layer / @upstash/ratelimit on Redis) enforce DfS 10 req/s, AI ~50 rpm, Apify concurrency.

The Cell decision (resolved fork): reuse TrackedLocation as the Cell (no destructive rename) + add freshness columns + introduce Discovery/DiscoveryCell. Add metroSlug and migrate the unique key city → metroSlug (the one risky migration: backfill then tighten).

Playbook detection — accuracy, rules & scalability (§4.15 detail)

The expert layer is a deterministic-first, evidence-mandatory engine. The product promise is "never an unverified accusation" — every finding carries the literal evidence, a computed confidence tier, and exposure-framed language.

Four invariants: (1) deterministic by default — gpt-5.4-nano only where no rule can decide (nuanced text), and only as a vote paired with the exact text it read. (2) null is first-class = "not checked" (missing enrichment or below floor) — never "clean", never "violation". (3) evidence is mandatory — a non-null verdict with empty evidence fails the test suite. (4) confidence is computed, not asserted.

The detect() contract

interface PlaybookSignal {
  key: string;                         // "hipaa.tracking_pixel_on_phi_page"
  group: "compliance"|"reputation"|"tech"|"competitive"|"ops";
  detect(ev: EvidenceBundle): SignalVerdict | null;   // pure; null = insufficient evidence
  falsePositiveGuards: ((ev) => {tripped: boolean; reason: string})[];
  pitchAngle: string;
  requiresEnrichments: ("tech"|"lighthouse"|"reviews"|"ads"|"cell"|"licenses")[];
  maxConfidence: "high"|"medium"|"low";   // new signals ship capped at "low"
  regulationRefs: string[];
}
interface SignalVerdict {
  value: number|boolean|string;
  confidence: "high"|"medium"|"low";
  evidence: EvidenceItem[];            // NEVER empty when non-null
  explanation: string;                 // exposure-framed, copy-linted
  corroborationCount: number;
}
// EvidenceItem.kind: review_quote | detected_script | failing_audit | dom_fingerprint
//   | license_lookup | ad_creative | cell_percentile | attribute | nano_reading
// Each carries the literal detail (the quote / script / audit id) + optional sourceUrl.

Confidence tiers (deterministic)

Tier Requirement
high ≥2 independent evidence kinds, ≥1 hard artifact (script/audit/license/fingerprint), thresholds cleared with margin, cell sample ≥30 (when cell-based)
medium exactly 1 hard artifact OR 2 soft signals agreeing; threshold cleared
low nano reading, OR a single soft signal, OR a hard artifact with a known ambiguity
null below floor → surfaced as "not checked" with the missing-enrichment reason

The driver enforces min(computedTier, signal.maxConfidence) — a maturing signal can never over-claim. A buggy detect() that throws is caught → null, never a false flag.

No-false-alarm — the 6 mechanics

  1. Corroboration floor before HIGH — one signal alone caps at medium; nano-only caps at low.
  2. Confidence tiers tied to evidence strength (table above).
  3. Conservative defaults — absence ≠ evidence (no license row ≠ unlicensed → null unless that state board is covered).
  4. Evidence always shown — the exact review quote (initials/stars/date), the named script (fbq('track','Lead') on /booking), the failing audit (color-contrast: 14 nodes), with a click-through.
  5. Exposure phrasing — a copy-lint (scripts/playbook-copy-lint.ts) fails the build on absolutes ("is violating / illegal / non-compliant / guilty").
  6. Cell-sample gating — any cell-percentile signal returns null when the benchmark sample < 30.

Flagship: HIPAA — pixel on a PHI page (contested → exposure-framed)

Composite: health category + third-party tracker (Meta/TikTok pixel, weight 0.55; GA4 on health, 0.30) co-located with a PHI page (booking/intake/portal tool on a path like /book·/appointment·/intake·/patient·/portal, weight 0.40). high only when tracker + PHI-page co-location is confirmed on the same path; medium when pixel + booking present but co-location unconfirmed.

False-positive guards (all must pass): marketing-only page where the tracker fires (no PHI path on origin) → null; no website / no tech → null; aggregator host (Yelp/Healthgrades) → null; consent manager detected (OneTrust/Cookiebot) → drop one tier, never high.

Why exposure, not violation: the June-2024 AHA v. HHS ruling vacated OCR's "proscribed combination" pixel guidance (OCR withdrew its appeal Aug-2024), so the federal theory is genuinely contested — but the class-action / state-privacy exposure is very real ($100M+ in 2023–25 settlements: Advocate Aurora $12.225M, HealthPartners $6M, URMC $2.85M). We flag it as "potential exposure worth checking" with a "legal landscape evolving" footnote — flagging a certainty would be both wrong and a liability.

ADA web-accessibility risk (cross-vertical, every playbook)

3,117 federal web-accessibility suits in 2025 (+27% YoY); we score only the audits cited in complaints, by failing-node count:

Lighthouse audit Complaint mapping Severity
image-alt alt-text (89% of complaints) serious
label form labels (72%) serious
link-name / button-name keyboard/SR nav (61%) serious
color-contrast contrast (68%) serious
meta-viewport zoom (mobile) serious
tap-targets, document-title, html-has-lang SR/mobile orientation moderate (never alone raises risk)

Tiers: high = ≥3 serious audits failing & ≥25 failing nodes · medium = 2 audits OR 10–24 nodes · low = 1 audit <10 nodes · null = 0 serious failures (we never flag "clean enough"). Restaurants lead all filings → ADA is the headline signal for that playbook.

Extension recipe (ship a 6th vertical)

  1. Create modules/playbooks/definitions/{vertical}.ts exporting a CellPlaybook (id, version 1, categorySlugs, regulations, signals).
  2. Import the shared signals; write only the vertical-specific ones.
  3. Register in modules/playbooks/registry.ts (categorySlug → playbook) — the cron picks it up, no pipeline change.
  4. Add golden fixtures (positive_high · positive_medium · negative_clean · negative_guard_* · insufficient_null) and run pnpm test:playbooks.
  5. Extend the state coverage maps so uncovered states return null.

Confidence graduation: a signal ships maxConfidence:"low"; thumbs-down telemetry + golden fixtures validate its false-positive rate before raising the cap. Backlog (modules/playbooks/BACKLOG.md) lists what we deliberately don't fake yet: live health-inspection scores, actual on-wire PHI (we detect pixel+PHI-page co-location, not the payload → capped at medium), license validity (we detect display, not currency).

Reliability for the user — what we do & don't claim

  • Every finding = confidence pill + evidence drawer (literal artifacts + click-through source URLs) + the cited regulation. Tom verifies in 10 seconds before he says it to a prospect.
  • "Not checked" shown honestly with the reason — never implies a business is clean.
  • We never claim a business is violating any law; that a license is invalid (only that it isn't displayed); that PHI is actually leaking (only that the litigated pattern is present); anything from nano without showing the text it read.

13 · Resolved clarifications (post-critique)

The completeness critic flagged 7 refinements + 1 critical under-specification; all resolved here.

13.1Reachability gate — full semantics (blocks Phase 4)▶

Distinguish scan failed from scanned-and-empty with Business.contactScanStatus (PENDING|OK|FAILED|PARTIAL). isHidden is set only when contactScanStatus=OK AND reachableChannelCount=0 — a FAILED scan never hides (retried). Staleness: a fresh discovery (>90d or re-discovery) resets contactScanStatus=PENDING; isHidden recomputed each scan, never sticky. assertEnrichable: in a batch it silently skips hidden (records unitsSkippedHidden, never charges); on a direct call it returns HTTP 400 {error:"unreachable"}; never cancels the batch. Override: explicit logged forceEnrichUnreachable admin action (audit in EnrichmentRun.meta) — default UI has none. “Why hidden” shows hiddenReason.

13.3AI model — gpt-5.4-nano only▶

OpenAI gpt-5.4-nano ONLY for every AI step (intent/entity extraction, classification, copy/first-touch, any synthesis) — already connected via services/ai; no Claude/Sonnet/Opus or other LLM. web_search banned (free web_fetch only). Where nano isn't reliable enough, prefer a deterministic rule or defer the feature rather than switch models.

13.4Primary/secondary category rule — enforced in membership▶

Enforced in cellMembershipWhere / the persist-time cellKey stamp: primary category drives CellMetric attribution (no double-count); categoryIds[] powers secondary filtering.

13.6Wallet settlement▶

All settlement is internal CreditLedger journal entries (instant), never live Stripe refunds. type ∈ {HOLD, SETTLE, REFUND, TOPUP, EXPIRE, ADJUST}. Authorize → HOLD; complete → SETTLE actual + REFUND diff; a failed/timed-out job refunds the entire hold. Stripe touched only on TOPUP (the only human-required payments surface).

13.7Compliance pillar surfacing▶

Weight 0 in the composite score (never deducts) but shown as a comparative percentile badge + drives expert-signal filters and pitch angles. A compliance gap surfaces as a pitch hook, never silently lowers a number.

13.9Portal flow shape▶

The 8 stages are a resumable linear waterfall backed by Discovery state, but each section (/lists, /prospect, /signals, /touchpoints) is also independently reachable from the sidebar.

13.10Closed-status extraction▶

Business.openStatus extracted at persist from DfS work_time.work_hours.current_status; additive column (no risky migration); part of Phase 2.
