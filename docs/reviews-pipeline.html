Reviews Collection Pipeline

mapsly · v0.12.2 · 2026-05-27 · author Viktor + Claude

Architecture of how Mapsly gathers Google reviews for one business (qualify-time + manual single-trigger), bulk of 500 (admin action + weekly cron), and the failure modes covered along the way. Every box in the diagrams is a real file you can grep for. Score at the bottom.

Scorecard · current state

Correctness

8/10

Idempotent via pendingReviewsTaskId + tag-fallback for orphans (INC-2026-05-26). 12-month cutoff + cursor-stop applied at upsert. Race window exists if pingback arrives before the pendingReviewsTaskId write commits — tag-fallback recovers it.

Reliability · error handling

7/10

DfS client: 2× retries on 5xx/408/429 w/ exp backoff. Pingback returns 503 on 40602 task_not_ready → DfS retries; 200 on duplicate → DfS stops. No dead-letter queue for orphan tasks stuck > 1h.

Cost discipline

9/10

Every external call routed through withCronRun + incrementCost. Standard queue (10× cheaper than Live). Paid-location gate filters before task_post. Per-call ceiling ($0.05). No per-tier daily ceiling yet.

Scalability · bulk fan-out

6/10

Weakest link. Bulk-500 admin action processes sequentially in ONE server-action call (Vercel 60s default budget → timeout risk at ~50 businesses). Weekly cron is capped at 100, ok for now but won't scale to 2M+ catalog. Task #81 tracks worker fan-out.

Observability

7/10

CronRun per tick with cost + meta JSON, surfaced at /admin/cron-runs. Tag-fallback logs INFO on recovery. Sentry catches uncaught. Missing: "stuck pending pulls > 1h" surface, pingback-latency histogram, alert when webhook silent 24h.

Security

9/10

Pingback token verified via constant-time compare. Admin action requires ADMIN session. PII anonymized at persist (reviewerName → initials). Apex → www rewrite documented (prevents auth-header drop). No dangerouslySetInnerHTML on review text.

Overall · 74 / 100. Solid foundation. The scalability gap (sequential bulk fan-out) is the single biggest item blocking a real 500+ run today. Closing it gets us to ~88/100. Adding a stuck-pull surface + per-tier daily ceiling pushes past 90.

The convergence point · modules/reviews/trigger-pull.ts

Six idempotency / cost guards before we spend a cent:

1. Business exists?                  → no  → skip "not_found"
2. business.googleCid present?       → no  → skip "no_cid"      (can't query DfS)
3. pendingReviewsTaskId set?         → yes → skip "in_flight"   (pull already running)
4. mode=initial && already pulled?   → yes → skip "already_pulled"
5. shouldCollectReviewsForBusiness   → no  → skip "no_paid_in_location" (paid-cell gate)
6. POST /v3/business_data/google/reviews/task_post  ← finally spend $0.00075

Why Standard queue + pingback? Live queue would block the cron / route handler for 5–45min until DfS computed — Vercel kills the function at 300s. Standard queue lets us return immediately and catch the results when they're ready. As a bonus, Standard is ~10× cheaper per call.

Known gap · Task #81. The bulk admin action processes rows sequentially in ONE server-action call. Vercel's default function budget is 60s; at ~1s per task_post you start timing out around row 50. Today's safe ceiling is ~40 businesses per click. To unblock real 500-row bulk runs we need to enqueue the work (Vercel Queues / Inngest / the Boxly Worker fan-out pattern) and return immediately. The weekly cron is fine because (a) its budget is 300s, (b) it's capped at 100 businesses per tick.

Worker fan-out for bulk (Task #81) Replace sequential for…of with enqueue-and-return. Bulk action persists a queue row per businessId, returns immediately.
