The enrichment pipeline — how 1,000 leads get researched, reliably.

The portal UX is built. This is the execution layer underneath it: the dependency graph that orders every research, the queue that runs 1,000-lead bulk jobs on the shared Boxly worker, the governor that respects three vendors' rate limits, the credit ledger that never double-charges, and the admin panel that makes all of it observable — derived from a 12-agent deep read of the prototype, the Mapsly codebase, the Boxly worker, and every external-API failure mode, then hardened against an adversarial review that found three production-breaking bugs.

00Executive summary

What exists, what's broken, and the shape of the fix — in one screen.

8 / 9

EnrichmentJob — the unit the UI's progress + dot-strip need is never written

Mapsly's enrichment is already demand-driven and air-gapped — a user request mints rows and returns; a 2-minute cron (/api/cron/internal/dispatch) is the only consumer; no external API runs in the request path. That foundation is right. But the bridge from request to worker is thin, and four first-class subsystems the portal UX depends on are defined-but-dead or contradictory:

  1. No dependency ordering. The prototype's core promise — "can't run AI research before we have the DOM; can't derive review signals before reviews are pulled" — is not modelled anywhere. dispatch.ts runs families in a fixed code order with no DOM-first gate, so services/ai_research can fire on a lead whose DOM never landed.
  2. Bulk doesn't scale. processEnrichmentRun is a flat for…await loop inside one 300-second Vercel function. A 1,000-lead run does 1,000 sequential DOM fetches + AI calls — it times out, leaves the run RUNNING, and nothing re-claims it.
  3. Credits are never charged. holdCredits/settleRun/refundHold/authorizeEstimate are implemented and tested but have no callers. The cost-bar's "~494 credits" and the "No credits were spent" banner have no backing transaction.
  4. Progress is faked. /api/agency/jobs synthesizes a 0%→100% jump from a coarse run rollup. The per-stage checklist, the "23 of 61 leads," and the per-row coverage dots have no data source because EnrichmentJob is empty.
The fix in one sentence

Make EnrichmentJob the real unit of work (one row per family × business/cell), order it with a dependency DAG whose truth lives in Neon, fan it out as waves onto per-vendor Redis lanes on the long-lived Boxly worker, govern every vendor call through a distributed token bucket, and wire the already-built credit ledger with a per-job hold → settle-on-success → refund-on-failure guarantee — all observable through one correlation ID per research.

Design principle

Boxly stays the dumb executor; Mapsly owns the brain. The shared worker (NestJS + ioredis) gains only generic primitives — a Mapsly lane, dependency-gated dequeue, per-vendor rate buckets, a crash reclaimer. The DAG truth, the credits, and the tenant model all live in Mapsly's own Neon DB. This keeps Boxly reusable and keeps the money + business logic where it belongs. No fork.

The scheduler claims a job only when it's truly runnable

The DAG truth lives in EnrichmentJob rows. A job is claimable iff every hard dependency is terminal-satisfied, it is not fresh, the Redis idempotency claim is acquired, and its vendor has capacity. Edges reference a stable logical key (idempotencyKey), never a physical job id — so a re-minted parent transparently re-satisfies the edge (hardening B3).

// modules/enrichment/scheduler.ts — runs in the dispatch cron (no external API)
async function selectAndDispatch(limit = 200) {
  await promoteUnblocked();              // BLOCKED → READY, set-based, one SQL statement
  const ready = await prisma.enrichmentJob.findMany({
    where:{ status:"READY" }, take:limit,
    orderBy:[{ family:"asc" },{ createdAt:"asc" }],   // vendor-fair
  });
  for (const job of ready) {
    const vendor = VENDOR_OF[job.family];
    if (!(await vendorBucket.acquire(vendor)).ok)        // token bucket / breaker
      { await mark(job, "RATE_LIMITED"); continue; }    // no attempt++
    if (!(await claim(job.idempotencyKey)))                  // SET NX — cross-research dedup
      { await attachToCachedResult(job); continue; }       // → SKIPPED_FRESH
    await mark(job, "CLAIMED", { attemptsInc:1 });
    await enqueueToWorker(job);                          // bulk POST, returns at once
  }
}
-- promoteUnblocked: set-based, edges reference idempotencyKey (re-mint safe)
UPDATE "EnrichmentJob" j SET status = 'READY'
WHERE j.status = 'BLOCKED' AND NOT EXISTS (
  SELECT 1 FROM unnest(j."dependsOn") AS dep(key)
  JOIN LATERAL (SELECT status FROM "EnrichmentJob"
                WHERE "idempotencyKey" = dep.key
                ORDER BY "createdAt" DESC LIMIT 1) p ON true
  WHERE p.status NOT IN ('DONE','SKIPPED_FRESH','SKIPPED_CACHED'));

04Bulk · running 500–1,000+ businesses in one research

Your worry #1. The current flat sequential loop times out; this replaces it with wave-based fan-out and crash-safe resume.

The decomposition — and why only a third gets enqueued at t=0

Take a research of 1,000 leads across 4 cells, all 9 families. It materializes 6,012 EnrichmentJob rows — but enqueuing all of them at once would flood the queue with un-runnable work (3,000 tech/services/lighthouse jobs that would just dequeue, see no DOM, and bounce). So the DAG splits the fan-out into waves:

WaveFamiliesEnqueued whenItems
W0 rootscontacts + reviews per lead, + 12 cell jobsat mint2,012
W1tech · services · lighthouse per leadon that lead's DOM callback3,000
W2ai_research per leadon reviews ∧ tech ∧ cell-ads/serp done1,000
finalizersignal_compute (PLAYBOOK, $0)in-process on the W2 callback0 queue items

2,012 Redis items at t=0, growing to 6,012 jobs as waves unlock. And the 6,012 logical jobs map to far fewer vendor calls because adapters batch: a DOM run covers 250 URLs, tech is a $0 in-process parse of the captured DOM (0 vendor calls), cell families are 12 calls total.

Checkpoint & resume — escaping the 300-second Vercel limit

The cron never does the work. It becomes a thin mint + drain trigger (<2s): mint rows, enqueue roots, return. The vendor calls run on the long-lived Boxly worker, which has no 300s cap. Checkpoint state is durable in two places:

  • EnrichmentJob.status — the per-unit checkpoint. A crash mid-job leaves a RUNNING row whose Postgres leaseExpiresAt expires; the reclaimer flips it back to READY and re-enqueues (safe — every job is idempotent).
  • EnrichmentRun progress — recomputed from EnrichmentJob counts, never hand-incremented. Resume = "re-enqueue non-terminal jobs"; re-running the cron is the resume mechanism.

Fairness — a 1,000-lead run must not starve a 50-lead one

  • Weighted round-robin across researches (mapsly:fair:rr) — the worker services one job from the next research in the ring, so a 6,000-job run and a 50-job run interleave 1:1 per pass.
  • Per-research in-flight cap that counts only actively-running jobs (holding a slot/token), per-vendor-lane — so a DOM bottleneck (Apify, 4 slots) can't block the research's own reviews from progressing on the DfS lane (hardening H6).

05Queue & worker topology · extending Boxly

Your worry #2 (dependency-aware queues). A deep read of the shared worker, with a per-capability reuse verdict.

Boxly's worker is NestJS + ioredis: a custom Redis-LIST queue routed by type via Lua (strict priority + FIFO), a per-process semaphore (WORKER_CONCURRENCY=10), a retry-ZSET poller with exponential backoff, a forensic DLQ, an OpenAI circuit-breaker, and a webhook callback to the app. The transport, retry, and callback plumbing are genuinely reusable; the scheduling brain (DAG, vendor limits, per-cell caching, credit hold/settle, tenant tagging, progress) is what it lacks and what Mapsly adds — as a new module set alongside, not a fork.

⚠ The crash-durability gap — the #1 hardening item

In Boxly today, a task RPOP'd but not completed before a worker crash is lost — the lock expires, but the task is already off the list, with no re-queue. At 1,000-lead fan-out with 80–225s Apify runs, crashes mid-run are likely. The fix: make Postgres EnrichmentJob.leaseExpiresAt the authoritative reclaim source (the worker heartbeats it; the Redis lock is advisory), and a sweep flips RUNNING jobs whose lease expired back to READY. This converts "lost on crash" into "at-least-once with idempotent commit" — the prerequisite for running ≥2 worker replicas.

06Rate-limit governance · DfS · Apify · OpenAI

Your worry #4. Never trip a vendor limit; never let one research starve another; never hold a worker slot while throttled; never spend credits when a vendor is down.

One distributed token bucket per vendor in Upstash Redis (the in-process semaphore can't enforce a global rate across replicas). Each maps to the vendor's real limiter shape:

VendorShapeLimitOn exhaustion
dataforseorate (req/s), shared by submit + pollcap 10 / refill 8/s (20% headroom)defer retryAfterMs, free the slot, no attempt++
apifyconcurrency (run slots) + cost ceilingmaxConcurrent 4, lease > actor timeoutdefer ~1.5s; slot released on terminal callback
openairate (rpm), weight-aware, breaker in front50/min · ai_research = weight 2breaker-OPEN → defer + refund

The cardinal rule — a defer is always free

The request path never touches a bucket. On the worker, the gate order is breaker → admission → bucket (breaker first so an OPEN vendor spends zero tokens and zero attempts). On any defer, the worker re-queues with a jittered delay and releases the slot + lock — it never sleeps in-slot. A 1,000-lead OpenAI burst parks 950 jobs in the retry ZSET draining at 50 rpm while the 10 worker slots stay hot serving other vendors.

-- atomic token-bucket consume (lazy refill + paused-check), one round trip
if redis.call('EXISTS', KEYS[2]) == 1 then           -- vendor paused (outage / cost incident)
  return { 0, redis.call('PTTL', KEYS[2]) }  end
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tok = tonumber(b[1]) or cap
tok = math.min(cap, tok + (now - ts) * rate/1000)          -- lazy refill
if tok >= weight then
  redis.call('HMSET', KEYS[1], 'tokens', tok-weight, 'ts', now)
  return { 1, 0 }                                       -- allowed
else return { 0, math.ceil((weight-tok)/(rate/1000)) } end  -- caller re-queues at now+wait

Fairness — bucket caps total, admission caps each tenant's slice

The bucket alone is FIFO-blind. A second gate bounds per-tenant (agency) max-in-flight per vendor (DfS 3, Apify 1, OpenAI 5 × plan weight). A tenant at its cap defers even with a full bucket — leaving the bucket free for others. The two gates compose: bucket = total vendor throughput, admission = each tenant's share. A whale's run gets slower, never starves a solo agency.

Your worry #3. Three error classes, a reconciliation self-healer, and an exact mapping to every promise the UI makes.

Backoff: full jitter is mandatory

delay = random(0, min(BASE · 2^(n-1), MAX)). In-adapter layer 500ms→4s; worker retry-ZSET 10s→120s; OUTAGE defer = breaker reset. At 1,000-lead fan-out, lockstep retries turn a blip into a self-DDoS — jitter de-syncs the replicas.

The reconciliation sweep — the most important self-healer

The named hazard: a DfS reviews task is posted, but the pingback never arrives (firewall, our 5xx during the ping), so pendingReviewsTaskId is stuck forever and every future delta skips. The sweep is a cron pre-step (not a tight loop) that polls task_get directly (idempotent — never re-task_post): if it landed late → RECONCILED; if past the 24h death window → release the cursor, refund, re-mint a fresh task. The same pattern re-attaches to an Apify run past our boundary by runId — never relaunch (double-spend guard).

08Credit accounting · per-op, one-time & bulk

Your worry #5. Wire the dead-but-built ledger; make four UI promises literally true; never double-charge.

The four promises

1. "~494 credits" — an honest quote (fresh → $0, cells once, hard upper bound).
2. "A run your balance can't cover won't start — server-enforced."
3. "No credits were spent. Retry in 2 min." — charge only on usable results.
4. "Paid results are permanent — re-open for 0 credits."

Two ledgers, independent

CronRun.costUsd = provider dollars we actually paid (bill-before-decide). CreditLedger = user credits, held at mint, settled only on a usable result, refunded otherwise. They legitimately diverge: a walled Lighthouse can burn $0.06 of Apify and still refund the user's 1 credit. That divergence is the reliability promise.

A credit is a reveal-entitlement, not a fetch (per §10)

The charge is decided by per-agency entitlement (EnrichmentReveal): the first time an agency reveals a lead/cell-signal it pays the credit — even when served from cache (no vendor call, ~100% margin). Re-opening your own paid data is free forever. So a terminal job settles a credit on this agency's first reveal (whether DONE via fetch or SKIPPED_FRESH via cache) and refunds when the agency already owns it, the job failed, or the reveal returned no usable result. No-usable-result rule (gap found in the §17 stress-test): a contacts reveal that finds 0 reachable channels is not a usable lead → refund + hide it (consistent with "charge only on a usable result" and the reachability gate). Scoped to contacts only — an empty reviews/tech/ads result is itself a signal (a reputation/tech gap) and stays charged.

The lifecycle: hold the upper bound, settle per-job, refund the diff

Atomicity — the race the current code can't survive

Today's holdCredits does read → check → write in three steps with no lock: two concurrent runs against 100 credits, each wanting 80, both read "100 available," both pass, both hold → oversell. The fix is an atomic compare-and-set in one statement Postgres serializes:

-- one statement: the WHERE is evaluated inside the UPDATE → no oversell possible
UPDATE "AgencyWallet"
   SET "heldCredits" = "heldCredits" + ${credits}
 WHERE "agencyId" = ${agencyId}
   AND ("planCredits" + "rolloverCredits" + "purchasedCredits" - "heldCredits") >= ${credits}
   AND "spentTodayUsd" + ${estUsd} <= "dailyCapUsd";     -- daily cap, race-free, same statement
-- rowsAffected: 1 = won the claim · 0 = insufficient → 402 "needs N, you have M"

Settle is per-job (idempotent on (runId, jobId, type)), drawing down plan → rollover → purchased — the run-close path becomes a pure WHERE NOT EXISTS sweep, so a DLQ replay or the reconcile cron never double-settles (hardening B1). A partial 61-lead run where 52 contacts succeeded and 9 were walled settles 52 + 61 reviews + 8 serp = 121 credits and refunds the rest — the 9 stay retryable and are never charged.

Decision: no $2/$5 interactive gate for user runs

The prototype says "Credit-aware enrichment — no separate gate." For user-initiated runs the only gate is affordability (have credits → it runs). The $5 rule in cost-discipline.md is about provider cost needing Viktor's approval in the autonomous loop — it can't apply to an interactive user run. The provider-cost ceiling becomes a per-agency daily soft cap surfaced in admin, not a hard click-blocker.

The Vercel-Fluid rule (load-bearing)

Never hold a function open during an external wait. The request path mints rows, holds credits, does one bulk POST, and returns. Lost-result recovery happens in a short cron sweep that re-attaches by idempotency key — never an await actorRun() in a function. Quote computation batches its freshness probes into 9 queries, not 6,000 sequential findFirsts (hardening H5).

10Serve-from-DB · freshness · indexing

Don't re-discover, don't re-enrich, don't re-charge for data we already hold. Show what we have instantly — even if stale — and spend only on the gap.

Resolved — the cost-vs-entitlement split

You flagged it correctly: the earlier draft used one global freshness check for two different jobs, which would hand a new agency leads it never paid for, free. Fixed by separating cost-dedup (global — never re-fetch fresh data, for anyone; pure margin) from reveal-entitlement (per-agency — your first reveal of a lead is a credit, whether served from cache or fetched live; your own re-opens are free forever). You've revealed it beforeFree · re-open · no fetchShow stale free · Refresh = 1 cr (live fetch)
New to you1 credit · served from cache · ~100% margin · instant1 credit · live fetch · ~6 min

The bottom-left is the case you flagged: a new agency revealing data another agency's spend already put in our DB pays the normal credit and gets it instantly, while our marginal cost is ~$0. The data moat is monetized per reveal-to-a-new-customer; the cache win is our margin (this is exactly how Apollo/ZoomInfo sell the same record to thousands). "Paid results are permanent · re-open for $0" means your own paid results — top-left only.

What the customer sees — owned vs new

The cache/fetch split is invisible to the customer; it only changes speed and our margin. Their quote is simply owned-free vs new-1-credit:

Example quote line

412 leads · 280 already in your research (free) · 132 new (132 cr)

A speed hint shows which new reveals are instant: · 90 ready now (in our DB) · 42 ~6 min (live fetch) — same price, 1 credit each. Your own stale leads show their value badged "as of {date}" with an optional Refresh (1 cr). The entitlement is recorded per-agency in EnrichmentReveal (§12); SKIPPED_FRESH/SKIPPED_CACHED stay cost states (no vendor call), decoupled from the credit.

Read-path indexing — the fast lookup

The hot serve-from-DB query is "for this cell, the businesses + their per-family coverage." It resolves in two indexed steps, no per-lead probe loop (the §10 H5 batched-probe rule):

-- 1. cell membership — indexed on Business[cellKey] (exact) ; secondary via categoryIds[] GIN
SELECT id, rating, "reviewCount", website, "openStatus", "reachability",
       "contactsExtractedAt", "techScanLastAt", "reviewsLastDeltaAt"
  FROM "Business" WHERE "cellKey" = $1;          -- hundreds of rows, one index hit

-- 2. per-family coverage — ONE groupBy, indexed on EnrichmentJob[businessId,family]
SELECT "businessId", family, status, "freshUntil"
  FROM "EnrichmentJob" WHERE "businessId" = ANY($2)
   AND status IN ('DONE','SKIPPED_FRESH','SKIPPED_CACHED');

-- 3. cell signals — indexed on AdMarketRun[cellKey,platform,ranAt↓], LIMIT 1 per platform

Server-enforced "don't re-spend"

Three layers guarantee we never re-pay for data we hold, even if the client asks: the snapshot guard (Discovery.idempotencyKey) rejects a duplicate research; the scheduler's claim-time freshness re-probe (§10 M7) flips a now-fresh job to SKIPPED_FRESH just before dispatch; and the per-cell idempotency key dedups a cell run across leads and across concurrent researches. The "we will not perform a new discovery or enrichment if the data already exists" promise is enforced server-side, not trusted to the UI.

11Hardening · the adversarial review

Two critics attacked the combined design for race conditions, crash safety, and contradictions. The fixes below are baked into the sections above — this is the audit trail.

Blockers — would double-charge, oversell, or deadlock in production

BLOCKER B1 · Per-job settle, not per-run. The design shipped both a "ledgerSum guard" idempotency claim and a @@unique([runId,type]) — mutually incompatible: a DLQ replay's second settleRun either throws (rolls back → free leads + leaked hold) or double-charges. FIX settle/refund per EnrichmentJob.id inside commitJob; @@unique([runId, jobId, type]); run-close is a derived groupBy sum only.

BLOCKER B2 · Cell dedup must not follow a job id. If research B blocks on research A's specific cell-job and A crashes before its callback, B is orphaned in BLOCKED forever (hold leaked) — most likely on hot cells (Miami med-spa), the dedup's marketing case. FIX cell results are addressable by the research-agnostic AdMarketRun(cellKey, platform, windowBucket) unique key; followers poll that row and promote to SKIPPED_CACHED regardless of which physical job produced it. No "synthetic follow link."

BLOCKER B3 · DAG edges reference logical keys, not job ids. A re-mint (dead DfS task, DLQ replay) creates a new parent row with a new id; children still pointing at the old (FAILED) id stay BLOCKED forever. FIX dependsOn stores idempotencyKeys; promoteUnblocked joins on the latest terminal job per logical key (the JOIN LATERAL in §02). Invariant test: "re-mint parent → child promotes."

Where the proposed design sits vs. best practice

Meets / matches best practice

Durable job DAG with topological scheduling · distributed token-bucket rate limiting + circuit breakers · at-least-once delivery with idempotent commit · hold→settle→refund credit ledger · correlation-ID tracing + structured logs · stale-while-revalidate reads · pre-flight quoting with server re-quote · per-tenant fair-share + noisy-neighbor isolation. These are the patterns Stripe / Temporal / Inngest / well-run data platforms use.

Deliberate pragmatic trade-offs (why not 9.5+)

1. A custom Redis-list queue on the shared Boxly worker rather than a managed durable-execution engine (Temporal / Inngest / SQS+Step Functions). Reuse + cost win; the reclaimer closes the main durability gap, but it's hand-rolled. 2. The single-writer /api/worker/callback route is a throughput chokepoint (flagged for a Redis-stream inbox / sharding under sustained multi-research load). Both are conscious, documented, and reversible.

Bottom line

The current enrichment architecture is a solid skeleton with the load-bearing organs missing — the demand model and reviews are real, but the dependency graph, the bulk runner, and the entire money path are dead or broken, so it cannot ship paid bulk enrichment today. The proposed design is best-practice-grade and almost entirely additive — it wires dead code and adds a scheduling brain rather than rebuilding. The risk is execution, not design: the reclaimer (crash safety) and the per-job atomic credit ledger are the two items that must be exactly right before any paid bulk run goes live.

Nothing in the likely-reality set loses data or money

The two open risks are a small extra provider cost (S32, capped by ceilings) and a deliverability quality issue (S45, mitigated by a freshness gate) — neither corrupts the credit ledger or strands a hold. The load scenarios degrade to "slower," never "starved" or "stuck," thanks to per-vendor lanes + round-robin fairness + the reclaimer. The remaining build risk is execution fidelity on the two must-be-exact items from §16: the crash reclaimer and the per-job atomic credit ledger.
