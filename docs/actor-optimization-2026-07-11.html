2 · The website robot — by real use case

You asked the right question. Here's each situation — and you're already handling them well.

Case A · "Just get me the contacts" — already doing it right ✔

The situation: a normal small-business website, no protection. We just want the page so our backend can pull the email and phone.

What we do today — and it's correct: we try a free plain fetch first (no browser, no proxy, $0). The code says ~70% of business sites are open and this gets them for free. Only the ones that fail — Cloudflare-walled, empty, JS-only — fall through to the paid browser robot. That's exactly the cheap-first design I was going to suggest; you already built it.

What we achieve: nothing to add here. The paid browser only ever runs on sites that already refused the free fetch — so there's no easy saving left in this case. (The one maybe is in Case B below.)

Case B · "The site is behind Cloudflare" — good, two small tightenings

The situation: the free fetch bounced off a "checking your browser…" wall, so we bring out the real browser robot to get past it.

Tightening 1 — fewer retries. Today the robot retries a walled site on a fresh address up to 5 times. A site still blocked after 2 fresh addresses won't clear on the 3rd–5th — we're just paying. Drop to 2.

Tightening 2 — match identity to location. The robot's language/region should match the internet address it uses. Right now they can mismatch, which itself trips more walls. (The Facebook robot already does this; the website one doesn't.)

The one "maybe." Our free first-fetch is a plain fetch with a normal browser label. Some sites block that on sight but would answer a fetch that looks more like a real browser (a "TLS-impersonation" fetch) — without needing a full browser. That could rescue some sites from the expensive browser tier into a cheap one. But we don't know how many walled sites are "just picky about the label" vs. a real challenge that needs a browser. Cheap to find out — we already count free-vs-paid; just log why each site got kicked to paid. Measure, then decide.

What we achieve: ~half the wasted cost on hard sites (retries), fewer walls (identity match), and possibly a cheaper middle tier (the "maybe," after measuring).

Case C · "Audit the site's speed (Lighthouse)" — already correct ✔

Your question — does Lighthouse run on every read? No. It's a separate function that runs one site at a time, only when asked, and the code flags it as "the expensive path (~$0.06), reserved for walled sites." A normal contact read never triggers it.

What we achieve: nothing to change. One optional check: confirm the backend only asks for Lighthouse when a signal truly needs the score, not "just in case."

4 · The Facebook robot — the whole build story

You're right that the plan has to start from what already failed. Here's every attempt and what broke.

# What we tried What happened Lesson
1 Original robot — a full browser opens each Facebook page (images on) 73% failed A dead run burned up to ~$0.90; ~93% of that was just downloading Facebook's images/page weight. A full browser to fetch what is really one data request = wrong, expensive tool.
2 Skip the browser — post the data request directly (the "R1" attempt) blocked Facebook rejected the direct request every time. No gain. Caused two incidents. The direct shortcut hits a wall we still haven't fully explained (see move #6, appendix).
3 Stealth rebuild (Jul 6) — turn images back ON to "look human", keep one warm session cost regression 2 quick tests passed, but real spend on failed runs jumped 24× — cheap $0.02 failures became slow $0.90 ones. But it did confirm: a browser with zero images gets blocked more. Images-ON helps us look human — but on the old per-page design it cost a fortune. Keep the "human" idea, kill the per-page design.
4 Forensics (Jul 10) — deep review on real data diagnosis Confirmed wrong-transport root cause. Rebuild the transport around "one page-open, then fetch lightly."
5 New robot mapsly-meta-graphql (Jul 10) — open one page to get a "pass", then fetch data lightly; retry on a fresh address; quit fast 11/11 ok Market path now works: $0.009–0.075 a run, 20–72s (was 27% success). But: the direct fetch still gets rejected, so the "open one page and listen" trick is what carries it; and pulling a specific advertiser's actual ads still gets blocked (0 of 3). The rebuild fixed the cost and confined images to one page-open. Two walls remain (below).
6 Facet-first fix (v0.19.28) prod-only fail Keyword tests passed but real market runs failed — we asked it to resolve 20 businesses' pages, which Facebook blocks. Switched to one "who advertises here" query. Test with the real input shape, not the convenient one. (Bit us twice.)
7 Block cooldown + empty check (v0.19.29) tamed One market re-blocked 7×/hour. Added: wait 12h after 3 fails, plus a real "empty vs blocked" test. Some markets just block no matter what — stop paying to retry them.
8 Billing hotfix (INC-58) was blind Reading the wrong cost field — every run looked like $0.02. We'd under-counted Facebook spend ~40×. Read the right number; the safety cap depends on it.
Three walls that never moved — no matter what we tried:
  • The direct-fetch wall. Posting the data request directly always gets rejected. Every version works around it by opening a real page and listening in. We still don't know for sure why — one cheap 30-min test would tell us (appendix).
  • The "list only" wall. A keyword/market search only returns who advertises — never their actual ads. Facebook built it that way; no code changes it.
  • The "real ads" wall. The only way to get a specific advertiser's actual ad images is to look up their page directly — and that path blocks hard. And since we only use our own robots, there's no buy-around this. It's in-house or we accept it.

5 · The Facebook robot — what to do next

Given those three walls, and that we build everything in-house:

  • Trim the obvious waste first. On every good run we fire an extra "which address am I on?" request we don't need, and a page-lookup step with no time limit (move #3). Gets us: a little faster + cheaper on every run, zero risk.
  • Test the images question — carefully. Turning images off on the harvest paths could make wasted runs cost cents instead of ~$0.90, but images-ON is a proven anti-block measure. So this is a live A/B, not a code-and-ship (move #4). Gets us: either a real cost cut, or proof it's not worth the block risk. The new design already shrank this problem — so it may be minor.
  • Settle the direct-fetch mystery cheaply. A 30-minute test tells us if the wall is a fixable "fingerprint" issue or a hard Facebook rule (appendix, move #6). Gets us: either more ads per run (in-house), or certainty to stop trying.
  • Skip re-doing the expensive first step. Save the "pass" from one run and reuse it for other markets while it's valid (bigger in-house project). Gets us: one page-open shared across many markets.
  • Accept the "real ads" limit for now. With no rentals, per-advertiser ad images stay a hard, blocked path. Keep our robot as the "who advertises" list (which it's uniquely good at) and revisit creatives only if an in-house idea proves out. Gets us: honesty about what the product can deliver today.

Everything else about the new robot — quit-fast, retry-on-block, cooldown, the honesty check — is good and stays.

8 · The technical detail (for build time)

Skip unless we implement — the exact code-level backing.

Where cheap-fetch-first already lives (so we don't rebuild it)

modules/discovery/enrich-contacts.ts runs a two-pass flow: Pass 1 = freeFetchDom (services/dom-fetcher/free-fetch.ts) — a plain $0 fetch, 20-wide concurrency, static desktop UA, SSRF-guarded — over every target. It classifies 403/503 + Cloudflare markers + <500-byte bodies as blocked. Pass 2 = only the blocked remainder goes to fetchDomsForCell (the paid Apify browser actor). The result carries freeFetched vs actorFetched counts — so we can already measure the split; we just don't log the block reason yet (that's move #5's cheap prerequisite).

Why images-ON is deliberate (move #4 is test-first, not do-now)

The 2026-07-06 stealth rebuild explicitly chose to "block ONLY media/video (allow images/CSS/fonts — look human)" because "a browser that fetched ZERO images is the biggest bot-tell," and a live A/B "flipped a succeeding run to blocked" when images were off. So blocking images on the fallback navigation (a real page load) carries genuine block risk and must be A/B'd live (apify push + real runs), never shipped source-only.

Nuance that shrinks the prize: the expensive image burn was the old per-target-nav actor. The new actor already navigates once (the prime) then harvests over HTTP — so images-on is mostly confined to that one prime render. The remaining exposure is only when the prime fails to mint tokens and every target falls to a fallback nav with images. Real, but narrower than the old ~$0.90 headline — which is exactly why it's "test and size it," not "assume a big win."

The direct-fetch wall — likely cause + the 30-min test (move #6)

Our code assumes page.request.post "rides the browser's TLS/JA3 fingerprint." Research says it does not — Playwright's request context runs in Node's network stack, so it presents a Node fingerprint, and Meta's WAF scores TLS before it checks the login token. That plausibly explains why the direct POST always error-payloads while "open a page and listen to its own request" works. Our own prior notes blamed Meta server-validating the signature instead. Both plausible, different fixes — so test before investing:

  • JA3 echo test (~30 min): POST to tls.peet.ws via page.request.post vs via page.evaluate(fetch); compare the fingerprint.
  • If they differ → move the harvest into page.evaluate(() => fetch('/api/graphql', …)) so it runs in the real Chrome renderer (real fingerprint + same-origin cookies). In-house, no new dependency. Expect the direct path to start working → more targets per page-open.
  • If they don't differ → it's Meta's signature rule; stop chasing the direct path.
