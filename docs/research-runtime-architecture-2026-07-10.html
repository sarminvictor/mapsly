Enrichment runtime · start / track / finish · architecture review

Why researches feel slow to start & finish — and why WebSockets aren't the fix

2026-07-10 · code-verified against main (dispatch, kick-dispatch, progress route, Boxly worker, crons) + 2026 stack-options research · 4-agent analysis

Bottom line. Your three pains — can't start immediately, don't know when it finished, general delays — are ~97–99% an execution/dispatch problem, not a notification problem. The client already learns of changes within ~2s via polling. What's slow is that the work doesn't start or close on time: the immediate-start accelerator (kickDispatch) is dead in production (missing env), so every run waits 0–120s (avg ~60s, worst case ~13 min) for the */2 cron.

WebSockets/SSE address the wrong layer — they make notification faster, but notification isn't the bottleneck, and on this stack (Vercel functions get cut at the duration cap, Upstash-REST can't SUBSCRIBE) they'd reintroduce the exact problems your own ADR already rejected them for. The real lever is one config fix ([S]) plus a small close-the-gap code change ([S]). Overall system: 5/10 — dragged almost entirely by one broken accelerator, not by the architecture.

  • Finish (cell runs): meta_ads/serp close only on the next tick — the enrich-cell callback never calls closeRunIfDone

📡 Notification — already fast · leave it

  • Cost ~$0 (304 on no-change); self-heals from DB on a Redis miss
  • WebSockets would shave ~1.5s off a minutes-long run — imperceptible

One reliability hole found (worth a cheap fix)The progress route derives status as redis.status ?? run.status, but each tick re-seeds Redis with the non-terminal run status. If the single close-time terminal re-seed write is lost, Redis keeps RUNNING forever and masks the DB's terminal — the UI spins until a manual reload. Hits exactly your "don't know when it finished" pain. Cheap fix: make DB status authoritative when terminal (already fetched free in the ownership read).

4 "Why not WebSockets?" — the honest answer

They solve notification, and notification is already ~2s fast. A socket to the browser cannot make server-side work start sooner (pain 1) and cannot make a run close sooner than closeRunIfDone runs (pain 2). For a closed tab a socket doesn't exist at all — that's the email's job.

And on this exact stack they're actively wrong — which your own ADR already worked out:

  • Vercel functions get cut at the duration cap (300s default; 800s GA / 1800s beta on Pro Fluid) — a run lasts minutes-to-hours, so an SSE/WS handler held open gets killed and forces reconnect machinery you'd have to build anyway. Even Vercel's new native WebSocket beta (Jun 2026) is still duration-capped — it looks native but breaks at minutes-scale.
  • Upstash-REST Redis can't SUBSCRIBE — an SSE handler would have to poll Redis server-side in a loop: identical work to the client poll, but billed as held wall-clock instead of ~$0 304s.
  • The only socket-capable host you own is the Boxly DO worker (no cap) — which is exactly where the ADR says to terminate a socket if you ever genuinely need one. You don't, yet.

The verdict: keep poll+Redis. Fix the dispatch layer, and the existing 3–4s poll surfaces the faster start/finish for free.

6 The plan — ordered by impact-per-effort

  1. S  Set/verify prod env NEXT_PUBLIC_APP_URL + CRON_SECRET. The single highest-leverage change — collapses PENDING→RUNNING from 0–120s to seconds. The code already emits kick-dispatch.skipped · missing-env in Vercel logs; if it's there, this is it. (Your env action.)
  2. S  Exempt /api/cron/internal/* from Vercel Deployment Protection (or add a bypass token). Watch for kick-dispatch.rejected httpStatus:401 — if it appears, env was set but the kick is still refused at the edge. (Your Vercel setting.)
  3. S  Close the cell-run finish gap — /api/internal/enrich-cell calls closeRunIfDone on the last cell family, so meta_ads/serp close on callback instead of the next tick. (Code — I can do this.)
  4. S  Make DB status authoritative when terminal in the progress route (fix the Redis terminal-masking hole). (Code — I can do this.)
  5. S  Tighten dispatch */2 → */1 as a safety net (idle-gate keeps it cheap) + fire the completion email from closeRunIfDone via after() so away-users learn sub-minute. (Code + config.)
  6. M  Make START durable — enqueue the initial dispatch through the retrying Boxly worker at trigger time, replacing the fragile fire-and-forget fetch. Removes the single most fragile link. (Code — needs BOXLY_WORKER_* env.)
  7. M  Instrument it — emit enqueuedAt→firstRunningAt + finishedAt→clientObservedAt metrics with a Sentry alert if start-lag p95 > 30s, so the pain is measured and env drift surfaces immediately. (Code.)
  8. L  Strategic (optional): migrate the cron-polled queue to QStash or Vercel Queues — event-driven start + native retries, removes cron latency structurally. A bigger bet; only if the S/M fixes don't fully settle it.
  9. L/XL  Defer WebSockets/SSE entirely unless a genuinely sub-second multi-user collaborative surface ships (e.g. live lead-claiming). If it ever does, terminate the socket on the Boxly worker — never a Vercel function. Not warranted by the current pain.
Decisions for you(1) Approve the S-tier code fixes (steps 3–5) for a /ship — they're small and directly address "don't know when it finished". (2) Set the two prod env vars (step 1) — the biggest single win, and it also speeds discovery + retries across the board. (3) Decide whether the M-tier durability work (step 6) + instrumentation (step 7) is worth it now, or after you confirm step 1 settles the start-lag. The WebSockets question is answered: not now, and not on Vercel functions.
