Built, deployed, and validated a brand-new actor implementing the "prime once, harvest" architecture from the forensics report. On the keyword / cell path — the primary enrichment use case — it went from the old actor's 27% success + $0.90 timeout burns to 11/11 success at $0.009–0.075 per run, 20–72 s, zero timeouts. It returns the advertiser facet and real ad creatives, and emits the exact same dataset + RUN_SUMMARY contract, so adopting it is a one-line env change.

The build surfaced a genuinely non-obvious root-cause bug that also explains failures in the old actor pattern: opening a named cross-run KV store hangs under Apify's LIMITED_PERMISSIONS and jams the SDK's storage queue, silently blocking every later write. Fixing that was the difference between 0-record timeouts and a working actor.

2 What was built

A fully new Apify actor — apify-actors/meta-graphql/, name mapsly-meta-graphql — deployed as a separate actor so the live production one keeps running untouched. Same input schema and the identical dataset + RUN_SUMMARY contract as the old actor, so the app adapter (services/apify/meta-ad-library.ts) is a drop-in.

The architecture (forensics best-practice, adapted to what actually works)

Crawlee auto-nav → facebook.com/ (light, reliable) → ONE prime nav → Ad Library page → scroll → capture doc_id + intercept facet → retry-on-block (rotate IP ×3) → emit target[0] · HTTP/nav the rest
  • One navigation per run (not per target) — the prime nav is target[0]'s scrape, via a response interceptor. This is the core cost fix: the old actor navigated every target with images, blowing the 280 s budget.
  • Retry-on-block — Meta soft-blocks a session probabilistically (an IP is flagged or not). If the primed page withholds the facet, rotate to a fresh residential exit and re-navigate, up to 3× — break the instant data reaches. This lifted success from ~50% to 11/11.
  • Fast-fail + wall budget — a genuinely dead session exits in ~20–90 s (~$0.06), never grinding to the timeout. The $0.90 burn class is structurally impossible.
  • Real doc_id capture — harvested from the page's own scroll-triggered pagination POST (regex bundle-scraping failed), re-minted every run so Meta's rotation is a non-event.
  • Full observability preserved — RUN_SUMMARY (outcome, credsMinted, docId, modeMix), per-target target_status with mode + elapsedMs, the honest ok/empty_verified/partial/blocked/timeout taxonomy, Actor.fail() on block, and a KV BC_LAST breadcrumb that survives a SIGKILL. Debug trail gated behind input.debug so production datasets stay contract-clean.

3 The bug that mattered — a reusable lesson

Root cause · every first smoke test timed out at 0 records

The actor hung for the full 280 s producing nothing — not even the first breadcrumb — regardless of code changes. KV-store breadcrumbs (which survive SIGKILL) pinpointed it: the code reached init-done but never the next line.

The culprit: await Actor.openKeyValueStore("mapsly-meta-warm") — opening a named, account-level KV store (for cross-run datr warming). Under Apify's LIMITED_PERMISSIONS (how actor runs execute), that call hangs instead of rejecting, and the pending call jams the SDK's internal storage queue — so every later pushData/setValue (breadcrumbs and real scraped data) blocks behind it forever, even though the crawler runs and burns proxy.

Fix: drop the named cross-run store entirely (each run primes its own datr — it was a marginal optimization). Prevention: never open a named account-level storage in an actor run without a timeout guard; if a storage op can hang, it stalls all storage. Logged as an incident.

5 How to adopt it

  1. The actor is deployed and live (id QUHP4uf8sgdavSCVT). Nothing in the app points at it yet — production still runs the old actor.
  2. Adopting is a one-line env change: set META_AD_LIBRARY_ACTOR_ID=QUHP4uf8sgdavSCVT. The adapter already reads this env and the dataset contract is identical — no code change.
  3. Recommended rollout: flip the env on a preview/staging first, watch a few real cell runs in AdMarketRun, then promote. Optionally A/B by market for a day.
  4. Consider dropping the run memory 4 GB → 2 GB in runActor (the new actor holds one lightweight page, not a heavy multi-target crawl) to shave the compute slice further.
