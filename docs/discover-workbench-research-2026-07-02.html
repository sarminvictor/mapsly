4 · Signal & field library — "I can't even find the email"

You're right, and here's the exact reason. Email is a research output (a column + a drawer entry), not a signal. There is no goal card for it (grep has_email in the goal library = 0). The only way to "filter by email" is the coarse reachability = EMAIL_ONLY tier — which can't express "has any email", "has a verified email", or "has an owner email". For an outbound agency, a verified owner email is the single most valuable field — and it has no filter. Email exposure score: 2/10

The shape of the gap: captured ≫ exposed

The schema captures roughly 5× more queryable data than the 44 goal cards expose. Of those 44 cards, ~12 are roadmap (evaluate to null), 8 are synthetic, and 2 are effectively dead against real data (branded_only_traffic — the brand-query scan never runs; recurring_complaint_theme — the AI theme pass was retired). Why this is structural, not cosmetic: the signal vocabulary is Mapsly's moat — "a prospect whose site loads slow + reply rate 0% + a competitor moved into their building." But the moat data is collected and discarded at the filter layer, leaving a thin, sales-curated 44 cards where the most valuable outbound field (a verified email) can't even be targeted. Most fixes here are wiring — the registry signals and resolver cases often already exist; no new data collection.

The DB has a genuinely rich per-lead, per-family state machine — EnrichmentRun.unitsCompleted / unitsSkippedFresh / creditsCharged, EnrichmentJob.status (QUEUED/RUNNING/DONE/FAILED/SKIPPED_FRESH) + errorMessage, per-AI-stage rows. The UI throws all of it away and derives one boolean: "is there data?" family-coverage.ts:75 Transparency score: 3/10

Blind spot Consequence (exactly what you hit) Fix
Failed ≡ never-run — coverage excludes all non-DONE jobs An errored contact scan looks identical to an untouched one; errorMessage is never shown. Add per-family status (done / stale / failed / pending / none); red dot on failure with the error on hover.
Partial run reads as "nothing enriched" — the set summary uses an all-or-nothing rule You enriched some leads (best-N), but the family stays "Not yet" because the un-enriched remainder lacks it. Per-family fraction: "Contacts 148/200 · 12 failed · 40 not run" + a top-line "N of M fully enriched".

The good news: the per-run summary component (EnrichingStep) is genuinely well-built (7/10) — honest OK/PARTIAL/FAILED copy, a done/failed bar, a credit-refund receipt. The failure is placement: it's only reachable during the run and for 1.4s after, never when you return.

7 · Every research, scored — how we collect, how good

Cross-cutting theme: every family's plumbing is strong (cost discipline, freshness dedup, SSRF guarding, failure isolation). Every family's detection/attribution layer is regex / substring / fuzzy-match over a single static artifact — one homepage, one keyword, one listing blurb. The highest-ROI upgrades are all the same shape: render JS + look past the homepage before asserting a negative, and attach confidence to fuzzy attribution.

Booking-tools deep dive (your example), answered at code level. The "No online booking tool" card evaluates has_booking_widget → BusinessTech.category = 'BOOKING' — i.e. the on-site fingerprint, not the free GBP flag. That's the right choice for the pitch, but it inherits three fragilities: (1) booking widgets usually live on /book or /appointments, not the homepage — a homepage-only fetch never sees them; (2) a JS-injected Calendly/Acuity widget leaves no calendly.com string in the raw HTML, and JS only renders when the page is blocked — so an open site with a JS widget is fetched statically and mis-flagged "no booking"; (3) only 8 vendors have signatures (SimplyBook, Booksy, Fresha, Setmore, Zenoti, Jane… all produce false "no booking"). Net: the flagship booking list has a materially high false-positive rate. Best-practice (Wappalyzer-Next) renders headless Chromium + keys on vendor script-src hosts. Fix: gate has_booking_widget = false to "not computable" unless the DOM came from the JS-rendering actor, and probe booking subpages.

10 · The reworked, personalised workbench

Start from why the user is here: an agency owner searched a market with a specific pitch in mind (e.g. "med-spas with no booking tool + a slow site") and needs a short, trustworthy, reachable shortlist to sell to. The workbench should feel like "here are your matches, here's the proof, here's how to reach them." Not a generic grid.

1 · The list reflects the search

  • Your chosen signals are the evidence columns — and each is a filter and a sort key (best-match first, already default).
  • A "Narrow by your goal" rail of one-click chips: your signals + "has verified email", "reachable", verification quality.
  • Column manager + saved, shareable views (Apollo/Clay parity).

2 · Contacts are the point, so lead with them

  • A default Contacts column: verified email + best phone inline, with a verification badge; "＋N" opens the drawer.
  • Drawer lists every email/phone/social as its own link, each with a verification mark + "report wrong".
  • Empty contact cell = a clear click-to-enrich button, not a dead "— enrich".

3 · Status you can trust

  • Per-family status chips: fresh / stale / failed / pending / none — failure hover shows the error.
  • A persistent run receipt: "Last enrichment · 26 enriched · 3 failed · 5 refunded".
  • Partial runs read as progress: "Contacts 148/200 · 12 failed · 40 not run".

4 · Data you can send

  • NANP-validated phones (junk gone), schema.org-first extraction, subpage crawl, JS render.
  • 4-stage email verification → a "valid emails only" filter that actually means something.
  • Role classification: owner / front-desk / generic — so "reach a decision-maker" is a filter.
