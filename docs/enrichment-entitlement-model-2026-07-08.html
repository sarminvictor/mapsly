Research entitlement model — the missing revenue layer

How a new agency re-uses vs re-pays for research on a cell another agency already touched · current code vs the intended model · scored, scenario-tested, code-confirmed, with a phased fix · + two Free-tier changes (FT-1 · FT-2) · 2026-07-08
→ Review addendum (below): code-verified findings, strengths, 9 gaps (G1–G9, incl. the filter-layer leak), the corrected all-plans FT-2 model, and the owner decisions — plan simpler now (no migration/backfill). → Implementation checklist at the bottom.

One boolean is doing two jobs. A single global freshness check (isFresh() over a shared Business.*LastAt cursor) decides both “should we run the vendor?” and “should we charge the user?”. Because that cursor is stamped by whoever ran the scrape — with no agency tag — the result is the exact inverse of the intended model:

  • the highest-margin path (serving data we already hold, ~$0 vendor cost) currently earns $0;
  • a free discovery ($0, valid 182 days) is the only key needed to see, in the drawer / workbench / CSV export, every rival agency’s paid research — contacts, reviews, ads, SERP, site-speed — for free.

Review addendum — code-verified, scored, decisions folded in · 2026-07-08

A full architect + PM review ran this plan through 6 code-grounded verifiers + 6 independent lenses — every code citation below is confirmed against the tree. The model is directionally right; the gaps are where the plan under-scopes its own thesis. Owner decisions (2026-07-08) fold in and simplify it. This addendum supersedes the Migration callout and refines the Phased plan + Free-tier sections.

Verdict. The RUN-vs-CHARGE decouple is the correct abstraction, and the code confirms the exact inversion it targets: one alreadyFresh boolean sets both job status and cost (dispatch.ts:649), billable = total − fresh (estimate.ts:113), and the freshness cursor is global with no agency tag. The model scores 9; the plan as written is ~5 to execute — a handful of CRITICALs stand between it and a safe billing flip. None touch the model; all are scope + code-shape.

DECISIONS LOCKED — final calls (2026-07-08, Viktor) · authoritative; supersede any "recommended/open" wording below.
  • D1 · Entitlement = PERMANENT-view. hasEntitlement = a ledger row exists; viewing what you bought is free forever; a refresh charges only when the shared data is actually stale. G1 resolved — the isFresh(grantedAt) validity predicate is dropped; grantedAt is provenance only.
  • D2 · Charge model depends on context. (a) Research / enrich: the user pays for the research, not a guaranteed result — an empty research outcome still charges (no non-emptiness gate; supersedes G4's "don't charge on empty"). (b) Search everywhere: charge only for delivered quality leads (matched + contacts), never the requested count — ask 30, show 24 → charge 24.
  • D3 · Charge-per-agency = GO, and INVISIBLE in the UI. We may charge multiple agencies for one underlying research. Hard UI rule: the served-from-DB path must be indistinguishable from a live run — always show the normal "researching…" progress; never surface "cached / from index / instant / served-from-DB" anywhere. This kills the doc's "Instant — from Mapsly's index vs Live pull ~30s" pitch and the "speed is the only difference" framing — there is no visible difference at all. A served unit still animates a normal run and completes; CHARGED_FROM_DB + SKIPPED_ENTITLED count as "done" for progress. (ToS non-exclusive-license clause still advisable — owner's call.)

What the plan gets right (strengths)

  • Correct root cause, code-true. A single global freshness boolean genuinely inverts incentives — the best-margin serve-from-DB path earns $0 while a free discovery leaks rivals' paid research. Diagnosed, not hand-waved.
  • Right decoupling axis. RUN = isDbFresh (internal COGS) vs CHARGE = hasEntitlement (per-agency revenue) are genuinely independent.
  • Global storage + additive ledger. One shared copy, no agencyId on research tables — preserves the sell-one-scrape-N-times margin lever instead of N-copy write amplification across 2.1M businesses.
  • Reuses the existing isFresh predicate for grant validity — one freshness function, not a fork.
  • settle already excludes SKIPPED_FRESH from billing (dispatch.ts:1222,1287) — the per-business change lands on a precise, testable seam.
  • Self-aware — it names its own hardest risks (empty-payload, vendor ToS, rip-off perception) rather than hiding them.
  • FT-2 flat-billing plumbing is proven — the outreach synthetic-run (holdCredits → settleRun(inserted) → refundHold) is a live, working template.

FT-2 · "Search everywhere" — corrected model (all plans) · owner clarification 2026-07-08

What it is. A search mode for all plans — not free-only. The user picks signals and a lead count (no market to pick); we search our whole index across every market and return leads that match his signals and have contacts, at 1 credit each. Free tier is restricted to this mode (can't open new markets); paid tiers get it plus Target.

  • Cross-market, never one cell. If a market has 0 matches we keep walking the rest of the index until we hit the requested count or run out. (Correction: today's stub still resolves onto the discovery's 1–3 cells — raw-list.ts:66-67 · page.tsx:183 — so true all-markets search is a new keyset-over-all-Business build, exactly the doc's searchIndexLeadsAction.)
  • Charge only for what we deliver. Ask for 30, we full-match 24 → charge 24 (settleRun(insertedCount)).
  • Basic info only in the table — discovery (Maps profile) + contacts. Reviews / ads / SERP / site-tech are not shown; unlocking them on a lead's page charges per-family. So the flat 1 credit buys exactly what it shows — list membership + a contacts entitlement — which is not an arbitrage (no 10-for-1 leak) and is the entitlement model. Build FT-2 after the ledger (Phase 3).
  • Filter-entitlement rule (your question — code-confirmed leak). You can only filter by signals you're entitled to. In search mode that's the 40 BASIC signals (profile · rating · review-count · contacts); the 64 research-gated signals (reply rate, ad presence, rank, site speed…) are locked — you can't match on data you haven't paid for, even though our DB holds it from another agency. Today the code lets you: resolveMatches runs over a globally-hydrated business (signal-eval.ts:1931 — businessId-only, no agency scope) and the workbench evaluates the whole 105-signal library per lead (workbench-rows.ts:456). The gate lives at the verdict/filter layer, not the shared storage — see G9.

"Full match" trap. Keeping only leads that match every selected signal with no missing data returns ~0 in thin markets. Example: 4 signals, one can't compute on a small market → every lead drops. Fix: a threshold — keep leads matching the signals we can check, show "matched 3 of 4 · 1 no data," and say "up to N" (the free 50 credits are also shared with touchpoints).

Honest search-mode copy (replaces the current "reviews and signals already in" · MarketStep.tsx:292): "Pick your signals — we'll pull up to N matching leads from every market we've mapped, with contacts. You're charged only for the leads we actually deliver. Add reviews, ads or site data on any lead for extra credits."

The model, stated cleanly

Two decisions that today share one switch must become independent axes:

Decision Question Lever Who feels it
(A) Run the vendor? Is our DB copy of this unit fresh? Cost / margin (internal) Nobody — invisible to the user
(B) Charge the user? Does this agency hold a valid entitlement? Revenue The user — pays for what they receive

Storage stays global (one shared copy = our margin lever — unchanged). The only new per-agency object is an entitlement ledger. Serve-from-DB is our best-margin sale (full price, ~$0 COGS); the user’s only difference between “from our index” and “live pull” is speed.

The four quadrants (target behaviour)

Our DB copy is FRESH
(no vendor spend)
Our DB copy is STALE / absent
(vendor runs)
You already OWN this unit
(bought it before)
SKIPPED_ENTITLED $0 — already current Serve from DB. A “refresh” here is a free no-op — it’s fresh, we run nothing, so nothing to charge.
REFRESH = CHARGE $0 to view · refresh charges Viewing your copy stays free. A refresh re-runs the vendor (real cost) → charged. Charge tracks the run, not the click.
You DON’T own it
(new buy OR refresh)
SERVED_FROM_DB ← new CHARGE full · no vendor The inverted high-margin path. Grant entitlement. Today: $0.
QUEUED → DONE CHARGE full · run vendor Grant entitlement on success. (Correct today.)

Two rules do all the work: (1) the only free path is delivering data you already own — the bottom-left cell (we have it, you haven’t bought it) is the whole ballgame: $0 today, a full-price near-zero-cost sale in the target. (2) An owner is charged to refresh only when the data is outdated and we actually re-run the vendor (real work, real cost). Refreshing still-fresh data is a free no-op — we show “fresh” and run nothing, so there’s nothing to charge. (A non-owner still always pays to acquire a unit, even from a fresh cache.) owner decision · 2026-07-08 (revised)

Model risks — the honest counter-view

The mechanics are sound; these are the business judgments the model itself forces. Worth a deliberate call before Phase 2.

Risk Note / how to hold it
“Charging full price for instant cached data feels like a rip-off” once users realise the scrape ran weeks ago for someone else Defensible only if you sell the data + a freshness guarantee, not the act of scraping. Message it as “current, verified data, delivered instantly” — never surface “served from cache” as “we did nothing.”
“I paid a credit and got 0 contacts” — an empty cached payload still charges Serve-from-DB of a legitimately empty result bills full price with nothing delivered — feels worse than a fresh empty pull that at least looked like effort. Needs a policy: don’t charge (or half-charge) an empty unit, and split “we ran” from “we found” (S7) so empties can be retried.
Billing multiple agencies for the same one-time scrape — ethics + vendor ToS Economically it’s a per-agency license (defensible), but Google/Meta/DataForSEO ToS on redistributing scraped data — plus the optics of “double-dipping” — warrant an explicit data-license clause in the agency terms.
Refresh charges only when data is outdated — decided Owner decision 2026-07-08 (revised): an owner is charged to refresh ONLY when the data is stale and we re-run the vendor (real cost). If the copy is still fresh, refreshing is a free no-op — we surface “fresh · no update needed” and run nothing, so we don’t bill for work we didn’t do. Non-owners still always pay to acquire. Needs a clear per-family freshness state in the UI so users aren’t nudged to refresh fresh data.
Migration double-billing of existing customers void No longer applies — owner decision 1 (2026-07-08): no migration. All data + users are test; the DB is wiped before launch, so there is no existing customer to double-bill. The whole risk disappears with the backfill.
Trust cost of “locked” data we visibly possess Showing a competitor’s lead as “locked · N credits” while our index clearly has it can read as manufactured scarcity. Balance conversion pressure against the perception of gating data “you already have.” The teaser copy carries this.
